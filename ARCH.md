# ARCH.md: Протокол Netrunner

## Обзор

Netrunner использует кастомный протокол инкапсуляции, чтобы скрыть факт использования прокси. Трафик выглядит как обычный TLS-хендшейк, внутри которого передаются зашифрованные кадры (frames).

## Уровни протокола

1. ТРАНСПОРТНЫЙ УРОВЕНЬ (TLS Wrapper)

- Использует TlsBridge для имитации Handshake.
- Сервер и клиент обмениваются ECDH публичными ключами в ClientHello/ServerHello.
- После хендшейка инициализируются ключи сессии (ChaCha20-Poly1305).
- Все последующие данные передаются как TLS Application Data.

2. УРОВЕНЬ МУЛЬТИПЛЕКСИРОВАНИЯ (Frame)
   Каждый кадр внутри AppData имеет фиксированный заголовок и структуру:

- Auth Tag (16 байт): HMAC-подобный тег для проверки целостности.
- Stream ID (4 байта): Идентификатор потока (позволяет пускать много SOCKS-запросов в один туннель).
- Frame Type (1 байт): 0x00(Connect), 0x01(Data), 0x02(Close), 0x03(Heartbeat).
- Payload Len (2 байта).
- Padding Len (2 байта).
- Payload (динамическая длина).
- Padding (рандомные байты от 0 до 255).

## Алгоритм работы

1. ClientHello (клиент генерирует ключи -> ServerHello).
2. Обновление ключей сессии (ChaChaCipher).
3. Шифрование Frame целиком (включая заголовок и паддинг).
4. Упаковка зашифрованного буфера в запись ApplicationData.

## Безопасность

- Auth Tag проверяется на каждом входящем кадре. Если тег не совпадает, соединение немедленно разрывается (защита от MITM).
- Паддинг генерируется рандомно для каждого кадра, что исключает анализ длины сообщений.
