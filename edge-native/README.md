# netrunner-edge-native

Та же роль, что и у [`client-edge`](../client-edge) (Cloudflare Worker), но
как обычный сервис на арендованной VDS вместо привязки к рантайму Cloudflare
Workers — см. подробный doc-комментарий в [`src/main.rs`](src/main.rs) за
полным описанием топологии и протокола.

```
пользователь ──WSS──▶ Caddy (443, реальный TLS) ──WS(127.0.0.1)──▶ netrunner-edge ──NRXP/TCP──▶ netrunner-server (нода) ──▶ BACKEND_ADDR
```

## Зачем отдельная VDS, а не Cloudflare Workers

Cloudflare Workers сам даёт бесплатный настоящий TLS-сертификат и
IP-репутацию домена `*.workers.dev`/своего домена — но это тоже наблюдаемая,
привязанная к одному облаку точка входа. Смысл этого крейта — та же роль
(входная точка перед VPN-нодой, до которой не должно быть препятствий из
целевого региона), но на **свежей, ничем не скомпрометированной VDS**,
которую можно арендовать в любой момент под новым IP взамен заблокированной,
не завися от одного облачного провайдера и его политики.

## Два слоя маскировки — их важно не путать

1. **Входящая нога (пользователь ⇄ эта VDS).** Обычный WSS — WebSocket поверх
   настоящего TLS с ACME-сертификатом (см. `Caddyfile.example` ниже). Прячет
   протокол от DPI/ISP между пользователем и этой VDS: снаружи это просто
   HTTPS-сайт с WebSocket-эндпоинтом, ничем не примечательный, пока сама VDS
   (её IP/домен) не попадёт в блок-лист по репутации.
2. **Исходящая нога (эта VDS ⇄ настоящая VPN-нода).** NRXP — TLS-мимикрия под
   `DECOY_SNI` (см. `netrunner_core::edge`/`tlseng`, тот же протокол, что и у
   обычного клиента). Прячет **содержимое** хендшейка от DPI/посредников,
   инспектирующих трафик по пути.

**Важно: слой 2 НЕ прячет сам факт соединения от хостера этой VDS.**
Хостер видит netflow/файрвол-логи ("эта VDS открывает TCP на IP X:443") без
какой-либо расшифровки TLS — маскировка контента ClientHello тут не при чём.
Если конкретно хостер (а не транзитный DPI/ISP) — часть модели угроз, нужны
дополнительные меры вне зоны ответственности этого крейта, например:
- держать `VPN_NODE_ADDR` за CDN/фронтингом, а не голым IP (обратная сторона
  той же идеи, что и у Cloudflare Workers, но теперь только для ЭТОЙ ноги, не
  для всего пути) — тогда хостер видит соединение к IP известного CDN, а не к
  IP вашей ноды напрямую;
- ротация VDS/провайдера чаще, чем успевает накопиться репутация;
- выбор юрисдикции/хостера осознанно (то, что уже подразумевает сама фраза
  "арендованная VDS" в задаче — предполагается, что это уже сделано).

## Конфигурация

Только переменные окружения — ничего не зашито в бинарь и не передаётся
аргументом командной строки (аргументы процесса видны любому с доступом к
`/proc` на этой VDS; переменные окружения демона — только тому, у кого есть
доступ к `/proc/<pid>/environ`, то есть root).

| Переменная      | Обязательна | Назначение                                                          |
|-----------------|-------------|----------------------------------------------------------------------|
| `VPN_NODE_ADDR` | да          | `host:port` вашей VPN-ноды (`netrunner-server`), например `1.2.3.4:443` |
| `BACKEND_ADDR`  | да          | `host:port`, который нода откроет по `Connect`-кадру (ваш бэкенд/сайт) |
| `DECOY_SNI`     | нет (`www.debian.org`) | Домен-декой для поддельного `ClientHello` исходящей ноги      |
| `AUTH_TOKEN`    | нет (пусто) | Bearer-токен, только если нода поднята с `--require-auth`            |

`--host`/`--port` (CLI, не env) — где слушает сам процесс. По умолчанию
`127.0.0.1:8082`: предполагается, что перед ним стоит reverse-proxy (Caddy),
который слушает `0.0.0.0:443` сам и проксирует уже расшифрованный трафик сюда
локально — этот процесс никогда не должен напрямую держать приватный ключ TLS.

## Локальный запуск

```bash
cargo run -p netrunner-edge-native -- --host 127.0.0.1 --port 8082
```

```bash
VPN_NODE_ADDR=1.2.3.4:443 \
BACKEND_ADDR=account.netrunner-vpn.com:443 \
DECOY_SNI=www.debian.org \
AUTH_TOKEN=your-nrxp-bearer-token \
cargo run -p netrunner-edge-native
```

## Деплой на VDS (Caddy + Docker)

`docker-compose.yml` в этой же директории поднимает оба контейнера сразу —
скопируйте его и `Caddyfile.example` (переименовав в `Caddyfile`) на новую
VDS рядом с `.env`:

```bash
scp docker-compose.yml Caddyfile.example root@your-new-vds:/root/netrunner-edge/
ssh root@your-new-vds
cd /root/netrunner-edge
mv Caddyfile.example Caddyfile
# отредактировать домен в Caddyfile и создать .env (см. ниже)
docker compose up -d
```

`.env` рядом с `docker-compose.yml`:

```bash
EDGE_DOMAIN=your-fresh-domain.example      # домен, на который смотрит Caddyfile
VPN_NODE_ADDR=1.2.3.4:443
BACKEND_ADDR=account.netrunner-vpn.com:443
DECOY_SNI=www.debian.org
AUTH_TOKEN=your-nrxp-bearer-token
```

Обновление образа на уже развёрнутой VDS — `docker compose pull && docker
compose up -d`, тот же принцип, что и в `.gitea/workflows/deploy.yml` для
обычных нод (см. корень репозитория) — тут просто не автоматизировано через
CI, потому что каждая edge-VDS — по определению одноразовая/недолгоживущая
точка входа, а не часть постоянного `nodes.json`.

## Сборка образа вручную

```bash
docker build -f edge-native/Dockerfile -t netrunner-edge:latest .
```

(контекст сборки — корень `netrunner-proxy`, не эта директория — тот же
приём, что и у корневого `Dockerfile`, т.к. `cargo chef`/workspace видит все
крейты только из корня).

## Ограничения (те же, что и у client-edge)

- Один логический поток на WebSocket-соединение, не полноценный
  мультиплексор — см. doc в `client-edge/README.MD`, то же самое применимо
  здесь один в один.
- Один процесс = одна пара (VPN-нода, бэкенд).
