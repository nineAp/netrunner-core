# NRXP — спецификация протокола

🇬🇧 [English version](en/PROTOCOL.md)

Полное описание протокола Netrunner (NRXP, *Netrunner eXchange Protocol*):
что и в каком порядке передаётся по проводу, как выводятся ключи, как устроены
кадры, мультиплексирование, UDP-нога, mesh-маршрутизация и контрольная плоскость.

> **Источник истины — код.** Документ написан по исходникам `main`
> (`PROTOCOL_VERSION = 6`) и сверен с ними: каждое утверждение про формат
> снабжено ссылкой на файл/функцию, а поведение handshake дополнительно
> проверено запуском сервера и тестов (`cargo test -p netrunner-core`,
> 244 теста, все зелёные). Где число **не удалось подтвердить** живым
> захватом браузера, это помечено `[?]` — такие значения нельзя выдавать за
> «байт-в-байт как у браузера».

> **Про публичность.** Раньше проект сознательно не публиковал константы, смещения
> и метки (см. [SECURITY.md](SECURITY.md), раздел «Почему тут нет цифр»):
> именно из них строятся сигнатуры для DPI. Этот файл — побайтовая спецификация,
> и он эту политику **не соблюдает**. Стойкость к чтению от публикации не страдает
> (она держится на ключах), но «неразличимость» (раздел 11) частично держится на
> том, что искать нечего. Оставлять ли файл в публичном репозитории — решение
> владельца.

## 1. Обзор и слои

NRXP — прикладной протокол мультиплексированного туннеля. Снаружи соединение
выглядит как TLS 1.3-сессия браузера Chrome к обычному сайту; внутри — зашифрованные
кадры с потоками.

```text
┌───────────────────────────── клиент ─────────────────────────────┐   ┌────────── узел ──────────┐
│ приложение ─ TUN ─ userspace TCP/IP (smoltcp)                      │   │                          │
│        │                                                           │   │                          │
│   Connect/Data/Close/Credit ... (кадры NRXP, §5)                   │   │  кадры → TCP/UDP к цели  │
│        │                                                           │   │                          │
│   мультиплексор: до 4 «ног» на сессию (§6)                         │   │                          │
│        │                                                           │   │                          │
│   запись ApplicationData (AEAD, набивка) (§5)                      │   │                          │
│        │                                                           │   │                          │
│   поддельный TLS: ClientHello/ServerHello/CCS (§3)  ──────TCP──────▶   │  stealth-fallback → decoy│
│   UDP-нога: QUIC / RTP / raw (§7)                   ──────UDP──────▶   │                          │
└────────────────────────────────────────────────────────────────────┘   └──────────────────────────┘
```

Транспорты:

| Транспорт | Что это | Где описан |
|---|---|---|
| **TCP-нога** | основной; от 1 до `MAX_TUNNEL_LEGS = 10` параллельных TCP на сессию (по умолчанию 4, выбирает клиент) | §3–§6 |
| **UDP-нога** | необязательная; одна на сессию; QUIC/WebRTC-мимикрия или голый UDP | §7 |
| **Mesh (QUIC)** | узел ⇄ узел, настоящий QUIC, поверх него тот же NRXP | §8 |
| **WSS / MASQUE** | внешние ретрансляторы перед узлом | §10 |

Крейты: `core/src/crypto` (ключи, AEAD), `core/src/tlseng` (имитация TLS),
`core/src/nrxp` (кадры, кодек), `core/src/net` (мультиплексор, движки, mesh),
`core/src/quiceng`/`webrtceng`/`rawdgram.rs` (UDP-нога).

## 2. Версии протокола и совместимость

Версия — первый байт `session_id` в `ClientHello` (`session_id[0]`). Это версия
**поведения NRXP**, а не версия TLS. Клиент заявляет её, сервер читает до вывода
ключей и решает, по какой схеме идти. [К] `core/src/lib.rs`

| Версия | Что вводит | Тег `ClientHello` | `ikm` | AEAD данных |
|:-:|---|---|---|---|
| **2** | анонимная схема, один DH. Нет учётных данных ноды | HMAC от времени, ключ = 32 нулевых байта | `DH(e_c, e_s)` | ChaCha20-Poly1305, AAD = nonce |
| **3** | аутентифицированный хендшейк: секрет ноды + статический ключ (второй DH) | HMAC на `nrxp_secret` | `DH_eph ‖ DH_static ‖ "nrxp-v3-static-dh"` | ChaCha20-Poly1305, AAD = nonce |
| **4** | AES-GCM через `ring` | то же + метка v4 | `… ‖ "nrxp-v4-ring-aead" ‖ suite` | AES-GCM (по выбранному suite) или ChaCha, **AAD пустой** |
| **5** | предпочтение шифра клиента подтверждается тегом | то же + метка v5 + байт предпочтения | `… ‖ "nrxp-v5-cipher-preference" ‖ suite` | как v4, но suite обязан совпасть с предпочтением |
| **6** | политика mesh-маршрута клиента подтверждается тегом | то же + метка v6 + 3 байта | как v5 | как v5 |

Что реально заявляется:

* Клиент **без** учётных данных ноды → v2 (`PROTOCOL_VERSION_ANONYMOUS`).
* Клиент с учётными данными, сборка `ring-aead` (мобильное приложение, headless-клиент,
  сервер) → **v5** (`min(PROTOCOL_VERSION, 5)`); **v6** — только если задана
  непустая политика mesh-маршрута (`set_mesh_route_preference`).
* Сборка без `ring-aead` (wasm `client-edge`) → v3, всегда ChaCha. [К]
* Сервер принимает любую из версий; нода в **строгом режиме**
  (`PROXY_NRXP_STRICT=true`) отвергает v2 (см. [SECURITY_MODEL.md](SECURITY_MODEL.md) §5).
  Узел, у которого учётных данных нет вовсе, принимает только v2 и отвергает ≥ v4. [К]

Прочие пороги по версии клиента (`>=`, поэтому апгрейд нод и клиентов независим):

| Константа | Значение | Эффект |
|---|:-:|---|
| `MIN_VERSION_FOR_CCS` | 1 | обмен `ChangeCipherSpec` |
| `MIN_VERSION_FOR_COVER` | 2 | сервер шлёт cover-flight после `ServerHello` |
| `MIN_VERSION_FOR_STATIC_DH` | 3 | второй DH + ключевой тег |
| `MIN_VERSION_FOR_RING_AEAD` | 4 | AES-GCM допустим, пустой AAD |
| `MIN_VERSION_FOR_CIPHER_PREFERENCE` | 5 | `session_id[1]` = предпочтение шифра |
| `MIN_VERSION_FOR_MESH_ROUTE_PREFERENCE` | 6 | `session_id[2..4]` = политика маршрута |

**Правило эволюции.** Неизвестный байт типа кадра после успешной расшифровки
**рвёт ногу** (рассинхрон), поэтому новые типы кадров допустимо слать только пирам,
заявившим достаточную версию. [К] `nrxp/frame.rs`

## 3. TCP-нога: установление соединения

### 3.1 Последовательность

```text
Клиент                                                        Сервер (узел)
  │── TLS record: ClientHello (≈1.7 КБ, как Chrome 140) ───────▶│  проверка тега (HMAC, §4.2)
  │── TLS record: ChangeCipherSpec (14 03 03 00 01 01) ────────▶│  неверный тег ⇒ stealth-fallback (§3.8)
  │                                                             │  вывод ключей (§4.3)
  │                                                             │  пауза 5…40 мс (случайная)
  │◀── TLS record: ServerHello (127 Б) ─────────────────────────│
  │◀── TLS record: ChangeCipherSpec ────────────────────────────│
  │◀── 4 записи ApplicationData: cover-flight (§3.6) ───────────│  только для клиентов v≥2
  │   вывод ключей (§4.3)                                       │
  │── ApplicationData: Heartbeat(stream 0) "sid:leg:token" ────▶│  валидация токена (§3.7)
  │◀══════════ мультиплексированные кадры, AEAD (§5, §6) ═══════│
```

Клиент не ждёт cover-flight как отдельного события: оставшиеся в буфере записи
разбираются штатно как `Cover`-кадры и отбрасываются. [К] `perform_handshake_on_connection`

Таймауты: ожидание `ClientHello` на сервере — `TLS_HELLO_TIMEOUT` = **10 с**;
ожидание auth-кадра — `SECURE_HANDSHAKE_TIMEOUT` = **20 с**. [К] `net/constants.rs`

### 3.2 TLS-запись

Каждое сообщение на проводе — TLS-запись: `type(1) ‖ version(2) ‖ length(2) ‖ payload`.
[К] `tlseng/tls_record.rs`

| Запись | `type` | `version` | Где |
|---|:-:|---|---|
| Handshake (`ClientHello`) | `16` | профиль клиента: Chrome 140 → `03 01` (TLS 1.0, как у Chrome), Firefox/Safari → `03 03` | клиент |
| Handshake (`ServerHello`) | `16` | `03 03` | сервер |
| ChangeCipherSpec | `14` | `03 03`, тело `01` | обе стороны |
| ApplicationData | `17` | `03 03` | все данные |

Разбор принимает типы `14/15/16/17`. `ApplicationData` короче 17 байт отвергается
(минимум — тег AEAD + 1 байт). Ошибка типа/версии на разборе помечается
`ErrorAction::Redirect` — «похоже на не наш трафик».

### 3.3 `ClientHello`

[К] `tlseng/handshake.rs::ClientHello`, [И] размеры измерены запуском.

```text
TLS record header (5)            16 | 03 01 | len
Handshake header (4)             01 | len24
legacy_version (2)               03 03
random (32)                      локальная СОЛЬ клиента (для HKDF, §4.3)
session_id_len (1)               20  (= 32)
session_id (32)                  см. 3.3.1
cipher_suites_len (2) + список   16 значений: GREASE, затем набор Chrome 140
compression (2)                  01 00
extensions_len (2) + расширения  см. 3.3.2
```

Размер на проводе [И]: **1730 Б** для SNI `www.debian.org`
(record payload 1725), **1720 Б** для SNI из 4 символов; **+1 Б на каждый символ SNI**.
Паддинга RFC 7685 нет: профиль Chrome 140 задаёт `target_padding_len = 0`,
потому что ClientHello с PQ-долей весит ~1.7 КБ и в запрещённый диапазон 256–511
не попадает физически.

#### 3.3.1 `session_id` — где спрятан протокол

32 байта, раскладка [К] (`make_client_hello`):

| Смещение | Длина | Поле | Значение |
|:-:|:-:|---|---|
| 0 | 1 | **версия протокола** | 2 / 3 / 4 / 5 / 6 (см. §2) |
| 1 | 1 | предпочтение шифра | `0` auto, `1` AES-128-GCM, `2` AES-256-GCM, `3` ChaCha20-Poly1305 (при v≥5; иначе случайный байт) |
| 2 | 1 | режим mesh-маршрута | при v6: `0` по умолчанию, `1` direct, `2` two-hop, `3` до X хопов (иначе случайный байт) |
| 3 | 1 | число хопов | при v6: `0` / `1` / `2` / `3..=8` (иначе случайный байт) |
| 4–15 | 12 | случайные байты | `OsRng` |
| 16–31 | 16 | **тег аутентификации** | HMAC-SHA256, усечённый до 16 Б (§4.2) |

Значение `session_id` в JA3/JA4 не входит (в отпечаток идёт только его длина), поэтому
версия и предпочтения не влияют на отпечаток. `ServerHello` **эхом возвращает**
`session_id` клиента (так требует TLS 1.3).

#### 3.3.2 Расширения (профиль `CHROME_140`)

Единственный профиль в пуле ротации `BrowserProfile::ALL`: остальные
(`CHROME_131`, `EDGE_130`, `FIREFOX_130`, `SAFARI_17`) оставлены как образцы
структуры и **намеренно исключены** — у них нет постквантовой группы, то есть их
`ClientHello` не совпадает ни с одним живым браузером. Профиль выбирается один раз
на сессию по хешу `session_id` сессии. [К] `tlseng/profile.rs`

**Шифронаборы:** `GREASE`, `1301 1302 1303 c02b c02f c02c c030 cca9 cca8 c013 c014 009c 009d 002f 0035` (16 значений, GREASE первым).

**Порядок расширений** (`ExtensionOrder::CHROME_140`; **середина перемешивается на каждое
соединение**, крайние GREASE-слоты остаются на местах — как у Chromium с v110):

```text
GREASE(пустое)  ALPS(0x44cd)  compress_certificate(brotli)  psk_key_exchange_modes
supported_versions  status_request  server_name  renegotiation_info  SCT
extended_master_secret  ALPN  session_ticket  key_share  supported_groups
encrypted_client_hello (GREASE)  ec_point_formats  signature_algorithms  GREASE(1 байт 0x00)
```

| Расширение | Содержимое |
|---|---|
| `server_name` | SNI = `decoy_sni` клиента, открытым текстом (как у браузера) |
| `supported_groups` | GREASE, `X25519MLKEM768` (`0x11ec`), `x25519`, `secp256r1`, `secp384r1` |
| `key_share` | **`GREASE(1 Б 00)`**, **`X25519MLKEM768`: 1216 Б балласта**, **`x25519`: 32 Б — наш настоящий эфемерный ключ**. Общая длина расширения 1263 Б [К] |
| `signature_algorithms` | 11 значений: `0904 0905 0906` (ML-DSA-44/65/87), `0403 0804 0401 0503 0805 0501 0806 0601` |
| `supported_versions` | GREASE, TLS 1.3, TLS 1.2 |
| `ALPN` | `h2`, `http/1.1` |
| `ALPS` | `h2` |
| `encrypted_client_hello` | GREASE-ECH: `outer`, HKDF-SHA256, AES-128-GCM, случайные `config_id`/`enc(32)`/`payload(144)` |
| GREASE | один жребий на соединение; значение группы **обязано совпасть** в `supported_groups` и `key_share` |

**Балласт ML-KEM.** Реальный обмен ключами идёт по X25519; 1216 байт — не случайный
мусор, а *структурно валидная* клиентская доля `X25519MLKEM768`: 768 коэффициентов
< q = 3329, упакованных по правилам `ByteEncode₁₂` (FIPS 203), плюс seed ρ.
Случайные байты не прошли бы «проверку модуля» (вероятность ≈ 10⁻⁷⁶) и сами были бы
детектором. Настоящей ML-KEM здесь нет, на этот ключ нельзя выполнить
инкапсуляцию. [К] `tlseng/mlkem.rs`

**Сервер ищет ключ по структуре**, а не по подстроке: разбирает `key_share` как
`list_len(2) ‖ { group(2) ‖ key_len(2) ‖ key }*` и берёт запись `group == 0x001d`
длиной 32 (раньше поиск подстроки `00 1d 00 20` мог случайно сработать внутри
балласта — раз на ~3.6 млн хендшейков). [К] `SessionKeys::extract_peer_public`

> `[?]` Длина payload GREASE-ECH (144) откалибрована по одному захвату. **Снятие с Chrome 148
> ([PCAP_PROFILE.md](PCAP_PROFILE.md)) показало, что у браузера она случайна: 144/176/208/240 Б**, —
> константа 144 в сборщике является отличительным признаком (требует исправления).
> Профили Firefox/Safari по размеру не сверены с живым захватом.

### 3.4 `ServerHello`

[К] `ServerHello::from_client_hello`, [И] **127 Б** на проводе (record payload 122):

```text
16 | 03 03 | 00 7a                         запись Handshake
02 | len24                                 ServerHello
03 03                                      legacy_version
random (32)                                локальная СОЛЬ сервера
session_id_len (1)=20 + session_id (32)    эхо клиентского
cipher_suite (2)                           выбранный suite (§4.4): 1301 / 1302 / 1303
compression (1)                            00
extensions: supported_versions(002b)=0304,  key_share(0033)= group 001d + X25519 pubkey сервера
```

Серверный профиль `ServerProfile::MODERN`: suites `[1301, 1302, 1303]`, порядок сервера.
Перед отправкой — случайная пауза **5…40 мс** (мгновенный идеально детерминированный
ответ сам по себе отличал бы стек от настоящего сервера).

### 3.5 ChangeCipherSpec

Обе стороны шлют `14 03 03 00 01 01` сразу после своего hello (middlebox-совместимость
TLS 1.3, RFC 8446 App. D.4) — так делают браузеры. Только для пиров с версией ≥ 1.

### 3.6 Cover-flight сервера

Настоящий TLS 1.3-сервер сразу после `ServerHello` шлёт `EncryptedExtensions`,
`Certificate`, `CertificateVerify`, `Finished` — все под шифром, то есть записями с
content-type `17`. Без аналога наш сервер замолкал бы после 127-байтового hello, и
первую `ApplicationData` слал бы клиент (булев признак). Поэтому сервер (для клиентов
v≥2) шлёт **четыре записи `Cover`-кадров** точной длины. [К] `tlseng/decoy.rs::CoverFlight`

Длина записи (поле `length` заголовка) считается от типовой цепочки Let's Encrypt
ECDSA P-256 (`from_chain(&[1250, 1100], 72, 32)`): `4+2+7+17`, `4+1+3+Σ(3+DER+2)+17`,
`4+2+2+72+17`, `4+32+17`. Итого записи **`41 (30, поднято до минимума), 2385, 97, 53`**
байт; первый flight сервера на проводе — **127 + 6 + 46 + 2390 + 102 + 58 = 2729 Б**.
Длины одинаковы на всех ногах узла (детерминизм — свойство настоящего сервера).

> `[?]` Длины не сняты с живого сайта-приманки конкретного узла. Следующий шаг —
> измерить настоящий ответ decoy-сайта и воспроизводить именно его.

### 3.7 Auth-кадр

Первая зашифрованная запись клиента — кадр `Heartbeat` (тип `03`) в `stream_id = 0`
с payload (UTF-8):

```text
<session_id> : <leg_id> : <auth_token>
```

* `session_id` — 32 hex-символа (`{:016x}{:016x}` от двух случайных u64), один на всю
  сессию клиента (общий для всех ног);
* `leg_id` — число `0..MAX_TUNNEL_LEGS-1` (0…9);
* `auth_token` — Bearer-токен (JWT пользователя) или пустая строка; для mesh-пиров —
  заявка `mesh…:` (см. §8.1). Разбор — `splitn(3, ':')`, токен может содержать `:`.

Если сервер запущен с `--require-auth`, он валидирует токен у control-plane (§9);
иначе токен игнорируется полностью. Отказ — кадр `Close` на `stream_id = 0` с текстом
`auth_rejected: <причина>` и закрытие TCP; клиент по этому тексту помечает сессию
**фатальной** и перестаёт переподключаться с мёртвым токеном. [К] `handler.rs`

### 3.8 Отказы и stealth-fallback

| Ситуация на сервере | Реакция |
|---|---|
| `ClientHello` не разобрался / не TLS | stealth-fallback на decoy |
| `ClientHello` разобран, **тег не сошёлся** (чужой/сканер/устаревший секрет/сбой часов > ±2 мин) | stealth-fallback |
| неверный байт предпочтения шифра/маршрута, нет общего шифра | stealth-fallback |
| `ClientHello` не пришёл за 10 с (в т. ч. plain HTTP на порту) | stealth-fallback (с задержкой 10 с) |
| валидный хендшейк, auth-кадр неверен / не пришёл за 20 с | разрыв, `netrunner_auth_failures_total` |
| валидный хендшейк, токен отвергнут control-plane | `Close auth_rejected:` + разрыв |

**Fallback** (`handle_stealth_fallback`): уже прочитанные байты пересылаются первыми,
дальше соединение склеивается в обе стороны с декоем; мост закрывается после
`FALLBACK_BRIDGE_IDLE_TIMEOUT` = 60 с бездействия, одновременно не больше
`MAX_FALLBACK_BRIDGES` = 512 (лишние закрываются). Куда:

* режим **`relay`** (по умолчанию): на SNI из присланного `ClientHello`, если это
  правдоподобный hostname (не IP-литерал, `[A-Za-z0-9.-]`, ≤ 253), иначе на
  `--decoy-host`; порт **443**. Адрес резолвится и проверяется: loopback, private,
  link-local (`169.254.169.254`!), multicast, unspecified, broadcast, documentation и
  **собственные адреса узла** отвергаются (последнее — защита от петли «узел
  подключается сам к себе»);
* режим **`self-hosted`**: запрошенный SNI игнорируется, всегда один свой сайт.
  ⚠ В текущем коде пересылка на локальный сайт **не работает** (цель
  `--decoy-local-site` проходит через тот же SSRF-фильтр, который запрещает
  loopback, и подставляется как hostname) — см. [DEPLOYMENT.md](DEPLOYMENT.md) §6.4.

Тег проверяется **до любой асимметричной криптографии**: тяжелее HMAC на
неаутентифицированном вводе нет ничего, иначе проба сканера была бы усилителем DoS.

## 4. Криптография

### 4.1 Примитивы

Собственной арифметики нет; всё — стандартные реализации:

| Назначение | Примитив | Реализация |
|---|---|---|
| Обмен ключами | X25519 | `x25519-dalek` |
| Аутентификация узла | второй X25519 со статическим ключом узла | `x25519-dalek` |
| KDF | HKDF-SHA256 (RFC 5869) | `hkdf` |
| Теги `ClientHello` | HMAC-SHA256, усечение до 16 Б | `hmac`, сравнение — `subtle::ConstantTimeEq` |
| AEAD данных | AES-128-GCM / AES-256-GCM / ChaCha20-Poly1305 | AES-GCM — `ring`; ChaCha — `chacha20poly1305` (RustCrypto) |
| mesh-капсулы | HPKE Base: X25519 / HKDF-SHA256 / ChaCha20-Poly1305 (RFC 9180) | `hpke` |
| QUIC Initial | AES-128-GCM + AES-ECB header protection (RFC 9001 §5) | `aes-gcm`, `aes` |
| Затирание секретов | `zeroize` (`Zeroizing`, `ZeroizeOnDrop`) | `zeroize` |

### 4.2 Тег `ClientHello`

`tag = HMAC-SHA256(key, msg)[0..16]`, кладётся в `session_id[16..32]`.
Окно времени: `step = ⌊unix_secs / 60⌋`. [К] `crypto/session.rs::SessionAuth`

| Версия | `key` | `msg` |
|:-:|---|---|
| 2 (анонимная) | `auth_key` = 32 нулевых байта | `step` (u64 BE) |
| 3 | `nrxp_secret` (32 Б) | `"nrxp-handshake-v3"` ‖ `step` ‖ `random(32)` ‖ `client_eph_pub(32)` |
| 4 | `nrxp_secret` | `"nrxp-handshake-v4-ring-aead"` ‖ `step` ‖ `random` ‖ `client_eph_pub` |
| 5 | `nrxp_secret` | `"nrxp-handshake-v5-cipher-pref"` ‖ `[cipher_pref]` ‖ `step` ‖ `random` ‖ `client_eph_pub` |
| 6 | `nrxp_secret` | `"nrxp-handshake-v6-routing-policy"` ‖ `[cipher_pref, route_mode, route_hops]` ‖ `step` ‖ `random` ‖ `client_eph_pub` |

Свойства:

* **Привязка к соединению.** Под HMAC входят соль и эфемерный ключ клиента:
  перехваченный тег нельзя вставить в чужой `ClientHello`.
* **Привязка версии и предпочтений.** Метка зависит от версии, а предпочтения шифра
  и маршрута входят в HMAC — подмена этих байт на пути ломает тег.
  (Исключение — понижение до v2: см. §4.2.1.)
* **Окно.** Сервер перебирает `step-2 … step+2` (`AUTH_WINDOW_SIZE = 2`,
  `AUTH_TIME_STEP = 60 с`) — **5 кандидатов, ±2 минуты**, всегда **все пять**, без
  раннего выхода; сравнение через `subtle`, накопление результата через `Choice`.
  Ветвления по секрету нет.
* **Повтор.** Хранилища использованных тегов нет. Дословный повтор перехваченного
  `ClientHello` проходит проверку тега, пока шаг времени в окне (≈ 2–3 минуты
  после перехвата). Ключей атакующий при этом не выведет (у него нет приватного
  эфемерного ключа, а сервер подмешивает свежую соль), и auth-кадра у него не
  будет, так что туннеля он не получит — но узел **ответит как узел**
  (`ServerHello` + cover-flight, а не как decoy), то есть повтор работает как
  активная проба. См. [SECURITY_MODEL.md](SECURITY_MODEL.md) §4, §6.

#### 4.2.1 Анонимная схема и понижение

Тег v2 не содержит секрета: любой, кто знает формулу, посчитает его. Он нужен
только для совместимости на время раскатки. Пока нода **не** в строгом режиме,
активный посредник может переписать `session_id[0]` на 2 и увести соединение на
неаутентифицированную схему; `PROXY_NRXP_STRICT=true` закрывает это
(тогда `verify_handshake_tag` для v2 возвращает `false`).

### 4.3 Вывод ключей

[К] `SessionKeys::generate_keys`

```text
salt = initiator_random(32) ‖ responder_random(32)           64 байта; инициатор = клиент
ikm  = DH(e_local, e_peer)                                    v2
ikm  = DH(e_local, e_peer) ‖ DH_static ‖ domain [‖ suite_be16]   v≥3, где:
         v3: domain = "nrxp-v3-static-dh"            (без suite)
         v4: domain = "nrxp-v4-ring-aead"            ‖ suite
         v5, v6: domain = "nrxp-v5-cipher-preference" ‖ suite
       DH_static:  клиент  = DH(e_client_priv, S_node_pub)
                   сервер  = DH(S_node_priv,  e_client_pub)       (одно значение)
PRK  = HKDF-Extract(salt, ikm)
client_aead = HKDF-Expand(PRK, "client_aead", 32)
client_iv   = HKDF-Expand(PRK, "client_iv",   12)
server_aead = HKDF-Expand(PRK, "server_aead", 32)
server_iv   = HKDF-Expand(PRK, "server_iv",   12)
auth_key    = HKDF-Expand(PRK, "auth_key",    32)
```

`suite` — идентификатор TLS-набора, выбранного сервером в `ServerHello` (`1301/1302/1303`),
big-endian. Клиент: `tx = client_*`, `rx = server_*`; сервер — зеркально.

* **Forward secrecy.** Эфемерный приватный ключ расходуется `take()`/`burn()` сразу
  после вывода; `ikm`, ключи и IV лежат в `Zeroizing` и затираются на `Drop`.
* **Аутентификация узла** — второй DH: посчитать его может только владелец
  `S_node_priv`. Статический ключ **по проводу не передаётся** (клиент знает его
  заранее) и не является стабильным идентификатором в пакете.
* `PRK` дополнительно сохраняется как `datagram_root` для UDP-ноги (§7.2) — второй
  хендшейк UDP-ноге не нужен.

### 4.4 Выбор AEAD данных

Сервер выбирает suite и кладёт его в `ServerHello`; AEAD данных определяется им.
[К] `TlsBridge::wrap_server_hello`, `SessionKeys::set_tls_cipher_suite`; [И] проверено запуском.

| Версия клиента | Предпочтение | Результат |
|:-:|---|---|
| < 4 | — | всегда ChaCha20-Poly1305 (`AAD = nonce`, legacy) |
| 4 | — | первый из `[1301, 1302]`, который предложил клиент (AES-GCM обязателен) |
| ≥ 5 | `auto` (0) | AES-GCM: на практике **`1301` AES-128-GCM** [И] |
| ≥ 5 | `1`/`2`/`3` | ровно запрошенный suite, если он есть у обоих; иначе отказ → fallback |

Соответствие: `1301` → AES-128-GCM (используются **первые 16 байт** 32-байтного
ключа), `1302` → AES-256-GCM, `1303` → ChaCha20-Poly1305. [И] с `auto` у v5-клиента
выбрался `1301`; с `ChaCha20Poly1305` — `1303`; с mesh-политикой — v6.

Следствие для документации: **текущие клиенты по умолчанию шифруют данные AES-128-GCM**,
а не ChaCha20-Poly1305 (ChaCha — для v<4, wasm-edge и по явному запросу).

### 4.5 Nonce, AAD, счётчики, рекей

[К] `crypto/chacha.rs`

* `nonce(12) = base_iv XOR (0⁴ ‖ counter_be64)` — XOR на байты `[4..12]` IV.
  `counter` — u64, **отдельный на направление**, начинается с 0, растёт на каждую
  запись `ApplicationData`. Nonce **не передаётся**: обе стороны считают его синхронно.
* Следствия: повтор nonce при одном ключе исключён по построению; **пропуск,
  дубликат или перестановка записи** внутри TCP-ноги рассинхронизируют счётчики →
  AEAD-ошибка → нога сбрасывается (`ErrorAction::Drop`) и переподключается с новыми ключами.
* `AAD`: v≥4 — **пустой**; v<4 с ChaCha — сам `nonce`.
* **Рекей** (только AES-GCM): каждые `2²⁰` записей в направлении ключ и IV
  обновляются симметричным храповиком, без обмена по сети:
  `ratchet₀ = key`; `next = HKDF-Expand(ratchet, "nrxp-stream-ratchet-next", 32)`;
  `key = HKDF-Expand(next, "nrxp-stream-aead-key", 32)`;
  `iv = HKDF-Expand(next, "nrxp-stream-aead-iv", 12)`; счётчик → 0.
  Для ChaCha рекея нет (u64-счётчик не исчерпывается).

### 4.6 Пер-кадровый тег в заголовке кадра

Каждый кадр несёт 16-байтное поле `auth_tag` (§5.1). Отправитель заполняет его
`HMAC-SHA256(auth_key, ⌊unix/60⌋)[0..16]`. **Получатель в data-фазе это поле не
проверяет** (`RxCodec::decode_inbound` не вызывает `verify_tag`; поле лежит *внутри*
AEAD-открытого текста). Целостность, порядок и защита от повтора в data-фазе
обеспечиваются AEAD и счётчиком nonce (§4.5). Временное окно проверяется только на
`ClientHello` (§4.2). Ранние редакции ARCH.md/SECURITY.md описывали обратное;
исправлено. Для датаграмм поле всегда нулевое.

## 5. Запись и кадр

### 5.1 Кадр NRXP

Кадр — единица мультиплексирования; живёт **внутри** зашифрованной записи. [К] `nrxp/frame.rs`

```text
┌──────────┬───────────┬──────┬─────────────┬─────────────┬─────────┬─────────┐
│ auth_tag │ stream_id │ type │ payload_len │ padding_len │ payload │ padding │
│  16 Б    │   4 Б     │ 1 Б  │    2 Б      │    2 Б      │  N Б    │ 0..2¹⁶  │
└──────────┴───────────┴──────┴─────────────┴─────────────┴─────────┴─────────┘
 └────────────── FRAME_HEADER_SIZE = 25 ────────────────┘
```

Набивка — случайные байты в хвосте кадра (внутри AEAD); приёмник пропускает
`padding_len` байт. `payload_len` — u16, но обычный потолок payload —
`MAX_FRAME_PAYLOAD = 16360` (§5.2).

| `type` | Имя | Payload | Направление |
|:-:|---|---|---|
| `00` | **Connect** | UTF-8 `host:port` (имя или IPv4-литерал). Открыть TCP-поток | клиент → сервер |
| `01` | **Data** | байты TCP-потока, ≤ 16360 | оба |
| `02` | **Close** | пусто; на `stream_id=0` — текст `auth_rejected: …` | оба |
| `03` | **Heartbeat** | `PING` / `PONG` / пусто / auth-payload на `stream_id=0` (§3.7) | оба |
| `04` | **UdpConnect** | UTF-8 `host:port`. Открыть UDP-«сессию» | клиент → сервер |
| `05` | **UdpData** | одна UDP-датаграмма | оба |
| `06` | **Diag** | JSON-снапшот диагностики клиента; только `stream_id=0`; на сервере уходит в приёмник диагностики, на клиенте отбрасывается | клиент → сервер |
| `07` | **Credit** | `u32` BE — **абсолютный** лимит байт Data потока (§6.5) | приёмник → отправитель |
| `08` | **Cover** | пусто / случайные байты; приёмник молча отбрасывает | оба |
| `09` | **SecureConnect** | как Connect, режим strong privacy | клиент → сервер |
| `0a` | **SecureUdpConnect** | как UdpConnect, strong privacy | клиент → сервер |
| `0b` | **MeshOnionConnect** | HPKE-капсула (§8.4) | узел → узел |
| `0c` | **MeshOnionUdpConnect** | то же для UDP | узел → узел |

Любой другой байт типа ⇒ `Err("Unknown FrameType")` ⇒ нога сбрасывается.

**Идентификаторы потоков.** u32; клиент выдаёт **нечётные** (1, 3, 5, …), сервер —
**чётные** (2, 4, …), шаг +2. `stream_id = 0` зарезервирован под служебные кадры
(heartbeat, diag, reject). [К] `muxer.rs::IdGenerator`

**Целевой адрес.** DNS клиента — «фейковый»: приложению выдаётся адрес из
`100.64.0.0/10` (начиная с `100.64.0.1`, LRU 2000, TTL 60 с); при `Connect` клиент
восстанавливает по нему имя и шлёт **`host:port` с именем**. Резолвит имя **узел**
(нет DNS-утечки на клиенте). Если имени нет — `a.b.c.d:port`. [К] `client/src/net/dns.rs`

### 5.2 Запись `ApplicationData`

[К] `nrxp/codec.rs`, `nrxp/frame.rs`

* **Инвариант:** кадр никогда не пересекает границу записи, но **одна запись несёт
  один или несколько кадров** (`TxCodec::encode_batch`, жадная упаковка).
* Запись: `17 | 03 03 | len` + `AEAD(кадры ‖ набивка) ‖ tag(16)`.
* Потолок открытого текста записи `MAX_RECORD_PLAINTEXT = 2¹⁴ + 1 = 16385`
  (RFC 8446 §5.2: 16384 + байт content-type). С тегом 16 Б поле `length` максимум
  **16401** — ровно то, что видно у браузеров. `MAX_FRAME_PAYLOAD = 16385 − 25 = 16360`.
* Кадр, не влезающий в запись (крупный control-payload, например `Diag`), уезжает
  отдельной записью **без набивки**.
* Размеры порций: `TUNNEL_INTERLEAVE_CHUNK = 16360` (кратно payload кадра, чтобы не
  оставалось «хвостового» кадра 24 Б), `BRIDGE_READ_CHUNK = 4 × 16360`.

### 5.3 Набивка длин (`PadShaper`)

Длина записи едет открытым текстом, поэтому без выравнивания наблюдатель читает размер
каждого сообщения. [К] `nrxp/codec.rs::PadShaper`

* На **каждое соединение** (на каждый `TxCodec`) строится список возрастающих границ:
  пол `floor ∈ [96, 512]`; следующая граница = `текущая + gap`, где
  `gap = clamp(текущая × r, 24, cap)`, `r ∈ [0.07, 0.34]`, `cap ∈ [256, 640]`; `r` и
  `cap` **свои у каждого промежутка**; последняя граница — 16401.
* Запись добивается до ближайшей границы сверху; записи ≥ 16401 не трогаются.
* Набивка идёт в хвост последнего кадра записи (`padding_len`), под AEAD.
* Почему не аддитивный шум: квантование **скрывает** размер (множество длин → одна
  цель); у шума матожидание цели `длина + E[шум]` восстанавливается усреднением.
  Регулярность границ побеждена тем, что шага нет вовсе.
* Остаток: наблюдатель, собравший много записей одного соединения, восстановит
  *набор* его границ, но не шаг и не параметры других соединений. `[?]` Полная
  имитация распределения длин конкретного decoy требует живого захвата.
* `Cover`-кадры идут мимо шейпера: их длина задаётся точно (`encode_cover`).

### 5.4 Разбор на приёме

`RxCodec::decode_inbound` расшифровывает записи по одной в буфер `staging`, парсит
кадры и отдаёт первый; остаток живёт до следующего вызова (читатель крутит вызов до
`Ok(None)`). Поэтому батчинг на передаче не потребовал ни бампа версии, ни правок
приёмника. Любой провал AEAD или разбора после успешной расшифровки ⇒
`ErrorAction::Drop` (пересоздать ногу с нуля). Буфер чтения ограничен
`TUNNEL_MAX_BUFFER_SIZE = 1 МиБ` (защита от OOM).

## 6. Мультиплексирование и сессии

### 6.1 Сессия и ноги

Сессия = клиентский `session_id` (§3.7). **Нога** — одно TCP-соединение, в котором
идут записи многих потоков. На сессию — до `MAX_TUNNEL_LEGS = 10` ног (число выбирает клиент: `--tunnel-legs`, настройка приложения; по умолчанию `DEFAULT_TUNNEL_LEGS = 4`; узлы старше этого релиза принимают не больше 4, лишние ноги не регистрируются); сервер
склеивает ноги одного `session_id` в один `Muxer`. Старт ног со сдвигом
`LEG_STAGGER_DELAY (1 с) × id × U(0.6; 1.4)` (ровный шаг был бы метрономом).
Клиентские ноги держат `TCP_NODELAY`; на Linux/Android обе стороны ставят
`TCP_NOTSENT_LOWAT = 2 × 16360` и запрашивают у ядра
`TCP_CONGESTION = bbr` (`NR_LEG_CC=off` отключает; без модуля остаётся ОС-умолчание),
размер буферов сокета подстраивается под ≈ 2×BDP (`buftune`: пол 256 КиБ, потолок 8 МиБ).

### 6.2 Жизненный цикл потока (TCP)

```text
клиент                                  сервер
  Connect(sid=odd, "host:port") ──────▶  TCP connect к цели (таймаут 7 с)
  Data(sid) ────────────────────────▶    ... немедленно, не дожидаясь ответа (0-RTT на открытой сессии)
  ◀──────────────────────── Data(sid)    данные цели
  ◀──────────────────────── Credit(sid)  выдаёт ПРИЁМНИК (клиент) по мере потребления (§6.5)
  Close(sid) ◀──▶ Close(sid)             закрытие любой стороны
```

* Подтверждения `Connect` в прямом режиме нет; при ошибке подключения узел шлёт `Close`.
  Сервер шлёт `Close` и при **любом** завершении моста (EOF цели, write-timeout ноги,
  `STREAM_PAUSE_BUDGET`, эвикция по бэклогу) — иначе виртуальный сокет клиента навсегда
  застрял бы в `CloseWait`. UDP-цель резолвится с таймаутом 5 с.
* **Порядок `Close`/`Data`.** `Close` едет по приоритетному управляющему каналу ноги, но
  писатель ноги **не пускает его вперёд ещё не записанных `Data` того же потока**; мост
  держит привязку потока к ноге, пока `Close` не уйдёт (он обязан ехать той же
  ногой). На приёме `Close` = `Muxer::finish_stream`: потребитель дочитывает всё
  принятое и видит EOF (клиентский движок отдаёт EOF локальному сокету только после
  слива бэклога). Для `stream_id = 0` — немедленное снятие.
* Привязка потока к ноге **липкая**: `select_leg` кладёт `stream_id → leg_id` при первом
  кадре; порядок TCP-потока сохраняется без номеров последовательности в NRXP.

### 6.3 Выбор ноги, отказоустойчивость

[К] `muxer.rs::pick_leg`

* Оценка ноги `score = max(rtt_ms, 1) × (1 + load_factor)`; `load_factor` учитывает
  очередь писателя, байты у писателя, Linux `notsent` и недавнюю ретрансляцию.
* Кандидаты — все ноги со `score ≤ 2 × лучший`; среди них **round-robin** (пачка новых
  потоков в спидтесте расходится по ногам, а не липнет к одной).
* **Anti-domino failover** (`send_to_network`): умершая нога эвиктится, кадр
  переотправляется на соседнюю; поток не закрывается.
* **Graceful pause**: если легли все ноги, чанк удерживается и ретраится каждые
  250 мс до `STREAM_PAUSE_BUDGET = 30 с` вместо сброса потоков.
* UDP-кадры по TCP-ногам: не липкая привязка, а короткие **flowlets** — серия в пределах
  паузы остаётся на ноге, пока та не перегружена.

### 6.4 Heartbeat и health-check

* Писатель ноги шлёт `Heartbeat` с базой `HEALTH_CHECK_INTERVAL = 3 с`, **джиттер ±30 %**,
  множитель `1 + idle_streak` (максимум ×8) по числу простаивающих интервалов подряд
  (идеально ровный период — сам по себе признак).
* `PING` → `PONG` на **той же ноге**, замер RTT; ответ на чужой PING не засчитывается
  (иначе мусорный RTT попадает в `GLOBAL_MIN_RTT`). Пустой `Heartbeat` на сервере →
  пустой `Heartbeat`.
* `Muxer::perform_health_check` не шлёт `PING` ноге со свежим `PONG`
  (`LEG_PONG_FRESHNESS = 45 с`); таймаут ответа `HEALTH_CHECK_TIMEOUT = 20 с`. На
  полностью простаивающей ноге обрыв обнаруживается за ≈ 65 с, на нагруженной —
  первой же ошибкой записи.

### 6.5 Сквозное управление потоком (`Credit`)

[К] `net/credit.rs`, `Muxer::credit_gate`

Нога — одно TCP на много потоков и не может притормозить один медленный поток. Поэтому
**приёмник** сообщает отправителю окно кадрами `Credit`:

* Payload — `u32` BE, **абсолютный** лимит («можешь отправить суммарно до N байт Data
  этого потока», по модулю 2³², сравнение знаковой разностью). Идемпотентно: дубликат
  или запоздавший кадр лимит назад не двигает; потерянный чинится следующим.
* Отправитель без единого гранта **не ограничен** — старые пиры работают как раньше.
* Выдаёт кредит клиентский движок (направление «сервер → клиент») по мере того, как
  приложение **реально забирает** данные, и mesh-реле (на своём участке).
  Направление «клиент → сервер» кредитом не регулируется (его держит TCP-backpressure
  и бэклог потока на сервере 16 МиБ).
* Окно: старт `CREDIT_INITIAL_WINDOW = 1 МиБ`, минимум 256 КиБ, максимум 16 МиБ на
  поток, общий бюджет процесса 64 МиБ (`окно ≤ бюджет / число приёмников`); растёт по
  скорости потребления (`≈ 2 × байт за RTT`, как `tcp_rcv_space_adjust`). Грант
  отправляется при накоплении `окно / 4` (не меньше 64 КиБ) неанонсированных байт.
* `credit_gate` блокирует **только отправителя этого потока**; если грантов нет
  `CREDIT_STALL_FALLBACK = 600 с`, отправка идёт без ограничения (защита от сломанного
  пира, но не от паузы плеера).
* Для UDP кредита нет.

### 6.6 Очереди и бэклоги

| Что | Значение |
|---|---|
| канал потока и ноги | 16 сообщений (≤ 64 КиБ каждое); глубокие каналы давали +100 мс соседним потокам |
| бэклог потока на клиенте | 4 МиБ |
| бэклог потока на сервере | 16 МиБ |
| эвикция по бэклогу | превышение бюджета **и** нет прогресса `BACKLOG_STUCK_GRACE = 5 с` (проверка раз в 500 мс) |
| ожидание, пока локальный сокет примет данные | `BRIDGE_STREAM_WRITE_TIMEOUT = 30 с` |
| простой моста / UDP-сессии / соединения | 30 с / 15 с / 120 с |
| после EOF потребитель, игнорирующий его | `STREAM_EOF_LINGER = 30 с` |

### 6.7 Переподключение и смена сети

* Пауза перед переподключением ноги `LEG_RECONNECT_DELAY = 2 с`, backoff с
  джиттером (`RECONNECT_BACKOFF_BASE 2 с + U(0..1 с)`, экспонента с потолком
  `MAX_RECONNECT_BACKOFF_MS = 10 с`); «флапающая» нога (умерла быстрее `LEG_FLAP_WINDOW = 5 с`)
  уходит в экспоненциальную паузу; после 10 подряд неудач движок возвращает ошибку,
  внешний цикл заново резолвит DNS.
* Сторож сети (раз в 1 с) при смене локального IP (или разрыве адреса > 3 с) снимает
  все ноги и поднимает заново. Туннель без единой ноги `TUNNEL_DEAD_AFTER = 30 с` считается
  мёртвым (после смены сети — окно `NETWORK_CHANGE_DEAD_GRACE = 90 с`).
* `auth_rejected` помечает сессию фатальной: все ноги прекращают реконнект.
* Сессия без ног удаляется через `SESSION_CLEANUP_DELAY = 120 с`.

## 7. UDP-нога

Необязательный параллельный транспорт для `UdpData`. Если он не поднялся, UDP едет
по TCP-ногам как `UdpData` — ничего другого не требуется.

### 7.1 Лестница и установление

```text
1. QUIC-мимикрия ─┐ равный приоритет, выбор — честная монета (CSPRNG, не из секрета сессии)
   WebRTC-мимикрия┘
2. голый UDP (raw)
3. TCP-нога (UdpData по TCP)
```

* **Одна попытка на сессию**, без агрессивных ретраев (блокировка UDP обычно
  постоянна). Клиент пробует один движок; если за `DATAGRAM_LEG_HANDSHAKE_TIMEOUT = 3 с`
  не пришло **ни одной** расшифрованной датаграммы — raw; если и он молчит — остаёмся
  на TCP. Установочный `PING` переотправляется со смещениями 0 / 300 / 800 / 1500 мс.
* Второго хендшейка нет: ключи выводятся из `datagram_root` (§7.2); сервер находит
  сессию по 16-байтному `leg_token` и поднимает ногу на первой успешно
  расшифрованной датаграмме. Один UDP-сокет сервера (**тот же номер порта, что и TCP**)
  обслуживает все сессии; адрес пира читается на каждую отправку (роуминг за NAT).
* Классификация входящей датаграммы по первому байту: диапазоны QUIC short header /
  RTP (`128..191`, RFC 7983) / остальное (raw).
* Кадр `UdpData` > `MAX_DATAGRAM_LEG_PAYLOAD = 1150` Б уходит по TCP (без
  фрагментации); внешний UDP-пейлоад целится в ~1250 Б.
* Ранний `UdpData` может обогнать свой `UdpConnect` (тот едет по TCP): сервер
  буферизует до 256 потоков × 16 КиБ × 2 с.

### 7.2 Ключи UDP-ноги

[К] `crypto/datagram_keys.rs`

```text
root        = PRK основного хендшейка (datagram_root) ‖ negotiated suite
leg_token   = HKDF-Expand(root, "dgram-leg-token", 16)          (без метки движка!)
для движка E ∈ {quic, webrtc, raw}, попытки A (всегда 0 сейчас), info(x) = x ‖ 00 ‖ E ‖ 00 ‖ A_be16:
chain_c2s₀  = HKDF-Expand(root, info("dgram-chain-c2s"), 32)
chain_s2c₀  = HKDF-Expand(root, info("dgram-chain-s2c"), 32)
hp_c2s, hp_s2c = HKDF-Expand(root, info("dgram-hp-c2s"/"dgram-hp-s2c"), 32)   (QUIC header protection)
```

Метка движка нужна, чтобы mimicry-попытка и запасной raw не делили ключ и не повторяли
одноразовый ключ Poly1305 при совпадении счётчиков (баг #18). `leg_token` метки не
имеет: сервер ищет сессию по нему **до** расшифровки.

**Храповик** (симметричная половина double ratchet, без DH): на эпоху — 
`key = HKDF-Expand(chain, "dgram-epoch-key", 32)`, `salt = HKDF-Expand(chain, "dgram-epoch-salt", 12)`;
шаг — `chain' = HKDF-Expand(chain, "dgram-epoch-next", 32)`, старое значение затирается.
Смена эпохи — через `2²⁰` датаграмм на направление. Компрометация ключей эпохи N не
открывает N−1; **не** даёт post-compromise security (храповик детерминирован).

### 7.3 Кодек датаграмм

[К] `nrxp/datagram.rs`

* `nonce = salt XOR (0⁴ ‖ counter_be64)`; полный 64-битный счётчик у отправителя, на
  проводе — только младшие `W` бит (16 для RTP-мимикрии, 32 для QUIC/raw);
  получатель восстанавливает полный счётчик алгоритмом QUIC (RFC 9000 App. A.3 / SRTP ROC).
* AAD — открытый заголовок пакета (так же, как в SRTP/QUIC). Кадр: тот же заголовок
  NRXP (25 Б, `auth_tag` нулевой), без набивки; AEAD — тот же suite, что и на TCP.
* Анти-повтор: скользящее окно **2048** датаграмм (как WireGuard), проверка только
  *после* успешной AEAD; продвижение эпохи коммитится тоже только после неё. Эпоха
  угадывается перебором соседних (`current` → `+1` → `−1`).

### 7.4 QUIC-мимикрия (`quiceng`)

* **Первый пакет** — настоящий QUIC v1 Initial (RFC 9000 §17.2.2): ключи Initial
  выводятся из публичной соли RFC 9001 и открытого DCID, шифр AES-128-GCM, header
  protection AES-ECB — любой QUIC-стек (и DPI) расшифрует его; внутри — наш
  `ClientHello` (тот же `TlsBridge::wrap_client_hello`) с ALPN `h3`,
  `quic_transport_parameters`, пустым `legacy_session_id`.
* **Дальнейшие пакеты** — QUIC 1-RTT short header (RFC 9000 §17.3.1): первый байт
  `0x40 | key_phase | (pn_len−1)`, DCID 8 Б (`QuicProfile::CHROME`, версия 1; половина
  `leg_token`: клиент → `[0..8]`, сервер → `[8..16]`), packet number 1–4 Б,
  защита заголовка маской ChaCha20 (RFC 9001 §5.4.4); sample берётся с смещения 4 от
  начала PN. 1-RTT-ключи не публичны, поэтому алгоритм HP ненаблюдаем.
* Один NRXP-кадр на пакет (коалесценции QUIC-пакетов нет).
* `[?]` Профиль QUIC не снят с живого захвата; `QuicMode::Real` (настоящий QUIC для
  self-hosted) — точка расширения, не реализована.

### 7.5 WebRTC-мимикрия (`webrtceng`)

RTP (RFC 3550): V=2, X=1 (заголовочное расширение one-byte `0xBEDE`, 1 слово),
PT = 96 (VP8, 90 кГц), `seq` со случайным стартом, `timestamp` по реальному времени,
`SSRC` из `leg_token` (клиент — байты `[0..4]`, сервер — `[4..8]`). AAD — весь RTP-заголовок (как в SRTP, RFC 7714). Номера
эпох на проводе нет — перебор; трейлера нет. `[?]` Профиль не снят с живого захвата
(Meet/Zoom/Discord), ICE/STUN/DTLS не имитируются; мимикрии временной структуры
(всплески на ключевых кадрах) нет.

### 7.6 Raw UDP

```text
leg_token(16) ‖ epoch_id(1) ‖ wire_counter(4) ‖ ciphertext
```
AAD — весь префикс. Никакой мимикрии (`RAW_DGRAM_OVERHEAD = 21 + 25 + 16`).
Существует потому, что чистый UDP местами проходит там, где не проходит QUIC- или
RTP-подобная форма.

### 7.7 Keepalive

На простое — `PING` с интервалом `U(15; 25 с)` (жёсткий период был бы признаком;
верхняя граница ниже типичного NAT-таймаута ≈ 30 с и `LEG_PONG_FRESHNESS`). Живость
отмечается любым настоящим кадром.

## 8. Mesh: маршрутизация между узлами

Mesh включается на узле флагом `--mesh-enabled` (требует `PROXY_NODE_ID`,
`PROXY_INTERNAL_SECRET`, `--backend-url`, а также NRXP-учётные данные). Узел-**ingress**
принимает клиента и по политике ведёт поток через цепочку узлов до **egress** — того,
чей IP увидит цель. Каталог пиров поставляет control-plane (§9).

### 8.1 Аутентификация пира внутри туннеля

Пир подключается к другому узлу как обычный NRXP-клиент (с `nrxp_secret` и
статическим ключом **получателя**, взятыми из каталога) и в auth-кадре (§3.7) шлёт
вместо токена заявку:

| Префикс | Грамматика поля `auth_token` |
|---|---|
| `mesh:` | `mesh:<peer_id>:<peer_secret>` — прямой egress, без маршрута |
| `mesh2:` | `mesh2:<peer_id>:<peer_secret>:<remaining_hops>:<selection>:<visited,csv>` |
| `mesh3:` | `mesh3:<peer_id>:<peer_secret>:<remaining_hops>:<selection>:<egress_id>:<visited,csv>` |
| `mesh4:` | `mesh4:<peer_id>:<peer_secret>` — onion-сессия: маршрут едет в капсулах (§8.4) |

`selection` ∈ `nearest`, `weighted-random`. Ограничения: `node_id` — `[A-Za-z0-9-]`, ≤ 64;
`peer_secret` ≤ 128 без управляющих; вся заявка ≤ 1024 Б; `remaining_hops ∈ [1, 8]`
(`MAX_MESH_HOPS = 8`); маршрут без петель (сравнение без учёта регистра), длина
`remaining_hops + |visited| − 1 ≤ 8`; предпоследний элемент `visited` обязан быть
самим пиром, последний — локальным узлом; `egress_id` не может встречаться раньше конца
пути; при `remaining_hops = 1` он последний, иначе — нет. Валидность секрета пира
проверяется у control-plane (`/mesh/validate`, кэш).

Готовность маршрута пир подтверждает `Heartbeat`-маркерами: `PONG` (legacy),
`NRXP-MESH2-READY`, `NRXP-MESH-ONION1-READY`; исчерпание резервных egress —
`NRXP-MESH-EGRESS-EXHAUSTED`.

### 8.2 Политика маршрута клиента

Клиент заявляет её в `session_id[2..4]` (v6, подтверждено тегом, §4.2):

| Режим | `[2]` | `[3]` | Эффект |
|---|:-:|:-:|---|
| по умолчанию (политика узла) | 0 | 0 | `--mesh-max-hops` узла |
| `direct` | 1 | 1 | 1 узел, без mesh |
| `two-hop` | 2 | 2 | ingress + 1 egress |
| `x-hop-N`, N ∈ 3..8 | 3 | N | длина пути случайна в `[3, N]` |

`--mesh-max-hops` узла — **жёсткий верхний предел** (`effective_max_hops = min`).

### 8.3 Выбор маршрута

На каждый прикладной поток ingress один раз выбирает egress и длину пути: кандидаты —
пиры со свежим (≤ 90 с) RTT-замером (`PEER_PROBE_MAX_AGE`), ранжирование по RTT и
взвешенный случай (`WeightedRandom`); при недостатке свежих данных — запасной
двух-узловой маршрут из каталога. Цепочка прикреплена к потоку на всю его жизнь.
Пиры, не ответившие на 3 пробы подряд, исключаются (`PEER_PROBE_TIMEOUT = 8 с`).
Сессии к пирам пулируются (≤ 256, простой 300 с).

### 8.4 Onion-капсулы

[К] `net/mesh_onion.rs`

Ingress строит маршрут **с конца**: каждый узел получает только свою инструкцию и
непрозрачную капсулу для следующего. Капсула — HPKE Base (RFC 9180):
`KEM = X25519-HKDF-SHA256`, `KDF = HKDF-SHA256`, `AEAD = ChaCha20-Poly1305`;
ключ получателя — его NRXP-`static_public`; `info = "netrunner-mesh-onion-v1" ‖ 00 ‖ node_id`
(капсула не переиграется на другое имя с тем же ключом); AAD пустой.

```text
wire      = enc(32) ‖ ciphertext          ≤ MAX_ONION_CAPSULE_SIZE = 12 КиБ
plaintext = version(1)=2 ‖ strong_privacy(1) ‖ is_udp(1) ‖ remaining_hops(1)
          ‖ expires_at_unix(u64) ‖ replay_nonce(16) ‖ kind(1) ‖ тело
kind=1  Forward: node_id(u8+str) host(u16+str) port(u16) decoy_sni(u16+str)
                 nrxp_secret(u8+str) nrxp_static_public(u8+str) next_capsule(u16+bytes)
kind=2  Exit:    target(u16+str ≤ 2048) failovers_left(u8) has_fallback(u8)
                 [ fallback_peer…(как Forward) ‖ fallback_capsule ]
```

Версия 1 (без резервных egress) читается для совместимости. Инвариант: `Forward`
допустим при `remaining_hops ∈ 2..8`, `Exit` — только при `1`; `has_fallback` ⇔
`failovers_left > 0` (≤ 7).

Отказоустойчивость egress: цепочка заранее выбранных резервных egress (до 7) зашита
капсулами; при неудаче подключения к цели узел-egress пробует следующий; сквозной
дедлайн установки потока — **65 с**.

Защита капсул: **срок жизни** `ONION_CAPSULE_MAX_AGE_SECS = 120` (проверяется по
`expires_at_unix`); **кэш повторов** по `replay_nonce` (до 262 144 записей, метёлка каждые
1024 вставок; при переполнении — отказ); маршрут с петлёй и протокольные нарушения
считаются метриками `netrunner_mesh_onion_*_rejections_total`.

### 8.5 Mesh QUIC

Транспорт узел ⇄ узел — настоящий QUIC (`quinn`, ALPN `nrxp-mesh/1`), UDP-порт
`--mesh-quic-port` (по умолчанию **8443**). TLS-сертификат эфемерный, самоподписанный
(`mesh.netrunner`), клиент **не проверяет** его: идентичность пира устанавливает
внутренний NRXP-хендшейк (§3–§4), без него mesh-сессия не принимается. До
аутентификации действуют лимиты: ≤ 512 одновременных соединений/хендшейков,
датаграммный буфер 256 КиБ приёма / 64 КиБ отправки. Порт слушает
**только mesh-пиров**: не-mesh заявка отвергается (`mesh_quic_non_mesh_rejected`).
Клиенты ходят на ingress по обычному NRXP (TCP/UDP), а не по этому порту.

### 8.6 Strong privacy

Режим клиента (`--strong-privacy`, `SecureConnect`/`SecureUdpConnect`):
маршрут идёт только через onion-капсулы (прямое открытие потока отвергается);
узел-ingress **перемешивает** кадры разных потоков окнами по `MIX_BATCH_WINDOW = 20 мс`
(≤ 512 пакетов; порядок внутри потока сохраняется), а на время активных потоков
шлёт на `stream_id = 0` фоновые `Cover`-кадры: интервал `U(0.9; 2.4 с)`, размер
`U(128; 384)` случайных байт. Цена — задержка.

## 9. Контрольная плоскость (HTTP-контракт)

Ядро знает только трейт `AuthValidator`; реализация в `server/src/backend_client.rs`
(`reqwest`) говорит с control-plane по HTTP. Любой совместимый бэкенд можно написать
самому. Все запросы несут заголовок **`X-Internal-Secret: <PROXY_INTERNAL_SECRET узла>`**
(секрет у каждой ноды свой; клиентам не выдаётся никогда).

| Метод и путь | Тело запроса | Ответ | Заметки |
|---|---|---|---|
| `POST /api/v1/internal/validate` | `{"token": "<Bearer>"}` | `{"user_id": str, "limit_bytes": u64\|null, "used_bytes": u64}` | успех кэшируется 60 с по токену; пустой токен отвергается локально |
| `POST /api/v1/internal/usage` | `{"user_id", "delta_bytes"}` | `{"used_bytes", "limit_bytes", "over_limit"}` | единичный отчёт |
| `POST /api/v1/internal/usage/batch` | `{"batch_id", "entries": [{"user_id", "delta_bytes"}]}` (≤ 1000) | список `{"user_id", "used_bytes", "limit_bytes", "over_limit"}` | пакетный отчёт трафика |
| `POST /api/v1/internal/node-health` | анонимная телеметрия узла (сессии, ноги, потоки, МБ вверх/вниз, счётчики ошибок, uptime) | любой 2xx | best-effort, без user_id/IP/целей |
| `GET /api/v1/internal/mesh/peers` | — | `[{"node_id","host","port","decoy_sni","nrxp_secret","nrxp_static_public"}]` | каталог mesh-пиров |
| `POST /api/v1/internal/mesh/validate` | `{"peer_id","peer_secret"}` | 2xx = принят | кэш успеха |

Circuit breaker: 5 подряд сетевых ошибок/5xx (4xx на конкретный токен **не** считается)
размыкают цепь на 10 с — дальше мгновенный отказ без HTTP-вызова
(`netrunner_circuit_breaker_open`). `over_limit = true` из отчёта о трафике — сигнал
сбросить потоки пользователя.

## 10. Edge-ретрансляторы и MASQUE

* **`client-edge`** (Cloudflare Worker, wasm) и **`edge-native`** (обычный сервис на VDS) —
  та же клиентская сторона NRXP без `tokio::net` (`core::edge::EdgeHandshake`): один
  логический TCP-канал до узла (ни мультиплексора, ни нескольких ног), входящая сторона —
  WebSocket поверх настоящего TLS (WSS). Хостер видит соединение VDS → узел.
* **`masque-edge`** — отдельный HTTP/3-релей для iOS Network Relay: TCP `CONNECT` и UDP
  `CONNECT-UDP` (RFC 9298), UDP остаётся в QUIC DATAGRAM. **Не NRXP**; свой токен
  (`MASQUE_AUTH_URL`/`MASQUE_TOKEN`), UDP/8444. Частные/loopback/link-local цели
  отвергаются по умолчанию (`--allow-private-targets` — только лаборатория).
  Экспериментальный, не production-hardened (ACL, rate limit, защита от UDP-усиления —
  впереди).

## 11. Что видит наблюдатель

Пассивный наблюдатель TCP-ноги видит: TCP:443; `ClientHello` ≈ 1.7 КБ с отпечатком
Chrome 140 (JA3/JA4 ротируются перемешиванием расширений, GREASE — случайный на
соединение) и SNI = `decoy_sni`; `ServerHello` 127 Б + `CCS`; затем **первую
`ApplicationData` — от сервера** (4 записи 41/2385/97/53 Б); далее записи
`ApplicationData` с нерегулярными квантованными длинами ≤ 16401. Heartbeat с
джиттером ±30 % и отступом ×1…8 на простое.

Что в этой картине **отличается от настоящего TLS-сервера** (честный список остаточных
признаков; подробнее и с оценкой — [SECURITY_MODEL.md](SECURITY_MODEL.md) §6):

1. **Сертификата нет.** Сервер не предъявляет цепочку; cover-flight лишь воспроизводит
   *размеры*. Любой, кто доведёт настоящий TLS-хендшейк до конца, обнаружит расхождение.
2. **SNI ↔ IP.** SNI — чужой сайт-приманка, который не резолвится в IP узла (детектор,
   стоящий один DNS-запрос). Лечится только собственным доменом на узле (режим
   `self-hosted`, который сейчас не работает — DEPLOYMENT.md §6.4).
3. **Активное зондирование владельцем клиента.** Тег проверяется на `nrxp_secret`,
   который есть у каждого клиента узла. Цензор, получивший валидный клиентский конфиг,
   может посчитать тег и классифицировать узел одной пробой.
4. **Длины записей** — остаточная статистика (§5.3); cover-flight не откалиброван по
   живому decoy `[?]`; размеры GREASE-ECH `[?]`.
5. UDP-мимикрия QUIC/RTP калибрована по спецификациям, не по живому захвату `[?]`;
   глубокий разбор упрётся в то, что за `ClientHello` нет `Certificate`/`Finished`.

## 13. Как это проверяется

```bash
cargo test -p netrunner-core --lib           # 244 теста, крипто/кадры/хендшейк/движки/mesh
cargo test -p netrunner-core --features ring-aead --lib   # включая AES-GCM-ветки
```

Ключевые тесты (имя → что фиксирует): `legitimate_handshake_succeeds_over_real_tcp`
(настоящий сервер на localhost, хвост после `ServerHello` целиком состоит из `Cover`),
`mitm_without_the_node_private_key_derives_different_keys`, `tampered_auth_tag_in_session_id_is_rejected_by_server`,
`chrome_client_hello_matches_the_live_capture_shape`, `record_lengths_share_no_recoverable_step_within_a_connection`,
`record_length_never_exceeds_real_tls13_maximum`, `server_close_neither_overtakes_data_nor_gets_lost`,
`sender_stops_at_the_credit_limit_and_resumes_on_grants`, `client_falls_back_to_raw_when_the_mimicry_engine_gets_no_reply`.

Нагрузка и поток под потерями/задержкой: `tools/loadtest`, `scripts/netns-stand/`.

Чего тесты **не** доказывают: постоянство времени проверки тега (оно живёт в машинном
коде; обеспечено конструктивно через `subtle`, измерять надо `dudect`/`cachegrind` на целевой
архитектуре) и «неотличимость» от настоящего браузера (нужен живой захват).
