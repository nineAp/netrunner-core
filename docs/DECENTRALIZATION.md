# Децентрализация: сеть, которая знает о себе сама

🇬🇧 [English version](en/DECENTRALIZATION.md)

Документ описывает, как сделать так, чтобы узлы и клиенты узнавали о сети из самого
протокола, а не из панели; какие у этого есть архитектурные схемы; и что из этого уже
реализовано (**этап A**, прототип в репозитории). Всё остальное — проект, не код.

> Статус: этап A реализован и покрыт тестами (в том числе три настоящих узла по loopback и
> три настоящих бинарника `netrunner-server`). Этапы B–E — предложение. Модель угроз и
> ограничения — в конце; прочитайте их до того, как полагаться на что-либо отсюда.

## 1. Что было и в чём проблема

| Что | Как сейчас (до этапа A) | Чем плохо |
|---|---|---|
| Клиент знает узел | один `remote_address` + `node_secret` + `node_public_key` из панели | заблокировали адрес — туннель мёртв |
| Узлы знают друг друга | каждые 20 с `list_mesh_peers()` из панели (`MeshPeer`: адрес, SNI, **`nrxp_secret`**, ключ) | панель — единая точка отказа и корень доверия; один взломанный узел узнаёт входные секреты всех |
| Допуск пира | `validate_mesh_peer()` в панели | без панели mesh не работает |
| Подлинность записи | нет: «запись из панели» | подписанной привязки «ключ ↔ адрес» нет |

Хорошо то, что каталог уже спрятан за трейтом `AuthValidator` (`list_mesh_peers`,
`validate_mesh_peer`) и цикл обновления в `server/src/network.rs` не знает, откуда пиры. Это и
использовано: этап A подставляет другой источник, ничего не меняя в маршрутизации, капсулах и
failover.

## 2. Принципы

1. **Подлинность отделена от доступности.** Запись самосертифицируется (подписана ключом узла),
   поэтому её можно нести любым каналом — проверка не зависит от того, кто принёс.
2. **Знание ограничено по построению.** Узел держит только то, что ему нужно; адреса мостов не
   пересказываются; из одной сети принимается не больше N узлов.
3. **Нет секретов в публичных записях.** Входной секрет соседа выводится из ключа роя (этап A) и
   далее из парного DH (этап C+).
4. **Первичный контакт неустраним.** Приложение и первый ключ входа — разовое событие доверия;
   его можно ослабить (воспроизводимая сборка, несколько подписантов), но не убрать.
5. **Sybil решается ценой, а не авторитетом:** приглашениями, поручительством, измеренным
   поведением, ограничением по сети — а не «кто главный».

## 3. Слои

```text
Слой 4  Доступ клиента     подписанные токены, проверяемые узлом офлайн             (этап B/E)
Слой 3  Рубеж (bootstrap)  несколько независимых каналов доставки подписанного набора (этап C)
Слой 2  Распространение    gossip узлов между собой + кадры внутри туннеля           ← этап A
Слой 1  Членство           кто вправе быть узлом: ключ роя → поручительство          ← A (ключ роя), D
Слой 0  Личность           node_id = H(sign_pub ‖ static_pub), запись подписана      ← этап A
```

## 4. Роли и гибридные схемы

Каждый может стать оператором, но с **выбором роли**; публичность — осознанный выбор, а не
следствие подключения.

| Роль | Кто | Публикуется? |
|---|---|---|
| **Лист** | любой клиент, особенно за NAT и в цензуре: только исходящие соединения | нет |
| **Ядро** | выделенные публичные узлы с хорошей полосой | да |
| **Друг-сторож** | пользовательский узел, вход только по приглашению | по токенам |
| **Скрытый оператор** | узел без публичного IP, держит исходящие связи к точкам встречи | нет |
| **Ретранслятор / выход** | добровольцы; выход включается явно | да, с пометкой |

Схемы собираются из этих кубиков; выбирайте по приоритету скорости и безопасности:

| Схема | Скорость | Безопасность пользователя | Стойкость к перечислению | Нагрузка на код |
|---|---|---|---|---|
| 1. Ядро + друг-сторож | высокая | высокая | средняя | низкая |
| 2. Две полосы (быстрая через ядро, приватная через x-hop) | максимальная для основного трафика | зависит от правил | средняя | средняя |
| 3. Скрытый оператор (точки встречи) | низкая | максимальная для оператора | высокая | высокая |
| 4. Мультипуть через разных сторожей | максимальная | средняя | средняя | низкая |
| 5. Кластеры + измеренная ёмкость | высокая | средняя | средняя | высокая |

Пресеты для пользователя: **Быстро** (ядро, 1–2 хопа, мультипуть), **Баланс** (друг-сторож → ядро
→ выход; чувствительное — в приватной полосе, по умолчанию), **Максимум** (лист → сторож →
2–3 ретранслятора → выход, перемешивание и cover), **Помощь сети** (роль оператора по выбору).

Правила безопасности пользователя: разные ключи и порты у клиента и оператора на одном
устройстве; лист по умолчанию, роль оператора — явным выбором; выход выключен по умолчанию;
сторожа стабильны (недели); квоты на полосу и потоки; связи узел–узел маскируются тем же
профилем браузера, что и клиент–узел; аварийная лестница (друг → скрытый оператор → временные
мосты через WebRTC → канал вне сети).

## 5. Этап A: что реализовано

### 5.1 Самоописание узла (`core/src/net/directory/descriptor.rs`)

Подписанная запись: `node_id`, статический ключ X25519, ключ подписи Ed25519, роли, признаки
(`GOSSIP`), диапазон версий NRXP, `seq`, `issued_at`, `valid_until` (≤ 72 ч), SNI-декой и
до 4 адресов. `node_id = SHA-256("nrxp-node-id-v1" ‖ sign_pub ‖ static_pub)[..16]` — запись нельзя
приписать чужому ключу. Ключ подписи выводится HKDF из приватного статического ключа узла:
отдельной настройки нет. Проверка: версия, личность, подпись (`verify_strict`), сроки (часы могут
расходиться на 5 мин), синтаксис адреса и публичность (`--directory-allow-private` для LAN).

Тесты: каждый байт записи покрыт подписью; подмена статического ключа ловится; фаззинг разбора не
паникует.

### 5.2 Хранилище и допуск (`store.rs`)

Побеждает больший `seq`; откат на старый адрес и повтор — «устарела». С одной сети (IPv4 /24,
IPv6 /48, домен второго уровня) — не больше 3 узлов; 2048 записей максимум, вытесняется
ближайшая к истечению (только если новая живёт дольше). Снимок на диск проверяется заново при
загрузке.

### 5.3 Обмен (`gossip.rs`) и кадр `PeerGossip` (0x0d)

```text
 инициатор                              отвечающий
  Digest{(id, seq)…}  ──────────────▶
                      ◀──────────────  Reply{записи, которых нет у инициатора; want: что нужно нам}
  Push{want}          ──────────────▶  (ответа нет)
```

Сообщение ≤ 15 000 байт (помещается в один кадр NRXP). Адреса мостов (`Roles::BRIDGE`) не
пересказываются. Входящие обмены ограничены по частоте. Кадр идёт по уже аутентифицированной
mesh-сессии (`MeshPeerSession::gossip_exchange`) и обслуживается только от mesh-пира.

**Совместимость.** Вместо повышения версии хендшейка использован признак `GOSSIP` в самой записи:
узлам без него кадр не шлют (неизвестный тип рвёт им ногу). Старые узлы из панели продолжают
работать как раньше.

### 5.4 Рой (`swarm.rs`) — вместо `nrxp_secret` в каталоге

`swarm_key` — общий 32-байтовый ключ сети. Входной секрет узла: `HKDF(swarm_key, "node-secret:" ‖
node_id)`. В записях секретов нет; участник считает барьер соседа сам; кто ключа не знает — не
проходит тег `ClientHello`. Допуск mesh-пира: он предъявляет секрет, выведенный для его `node_id`
(`DirectoryValidator::validate_mesh_peer`, сравнение в постоянное время).

> **Промежуточное звено.** Ключ роя — разделяемый секрет; его утечка снимает входной барьер сети
> (но не позволяет подменить узел: личность держит статический ключ в хендшейке). Любой участник
> может вычислить секрет любого соседа, т. е. допуск — «член роя», а не «именно этот узел». Этапы
> B–C заменяют его токенами и парными секретами.

### 5.5 Узел без панели

`DirectoryValidator` реализует `AuthValidator`: `list_mesh_peers` берёт соседей из каталога,
`validate_mesh_peer` проверяет секрет роя, учётные записи — из панели, если она есть (иначе
пользовательских токенов нет). Цикл в `server/src/network.rs` не изменился.

**Запуск.** Один раз на сеть: `openssl rand -hex 32` → ключ роя. Для каждого узла: свой
`PROXY_NRXP_PRIVATE_KEY` (`openssl rand -hex 32`).

```bash
export PROXY_SWARM_KEY=<ключ роя>
export PROXY_NRXP_PRIVATE_KEY=<ключ узла>

# напечатать самоописание узла (для соседей) и данные для клиентов
netrunner-server --port 443 --advertise 203.0.113.10:443 --print-descriptor
#   node_id / static_public / nrxp_secret / descriptor <hex>

# запустить узел, знающий соседа по его самоописанию
netrunner-server --port 443 --advertise 203.0.113.10:443 \
    --directory-seed <descriptor hex соседа | путь к файлу> \
    --directory-file /var/lib/netrunner/directory.bin
```

| Флаг (переменная) | Смысл |
|---|---|
| `--swarm-key` (`PROXY_SWARM_KEY`) | включает режим роя; не нужны `PROXY_NRXP_SECRET`, `PROXY_NODE_ID`, бэкенд |
| `--advertise` (`NETRUNNER_ADVERTISE`) | публичный `host:port` в самоописании |
| `--directory-seed` (`NETRUNNER_DIRECTORY_SEED`) | самоописания соседей (hex или файл; по записи в строке) |
| `--directory-file` (`NETRUNNER_DIRECTORY_FILE`) | сохранять каталог между перезапусками |
| `--directory-gossip-interval` | период обмена, секунды (±30 %) |
| `--directory-allow-private` | принимать частные адреса (LAN, стенды) |
| `--print-descriptor` | напечатать самоописание и выйти |

Метрики: `netrunner_directory_records`, `…_exchanges_total`, `…_exchange_failures_total`,
`…_records_learned_total`, `…_records_rejected_total`, `…_bad_messages_total`.

Проверено вручную: три настоящих бинарника по loopback, цепочка знакомств 1→2→3, через несколько
секунд у каждого по две записи, каталог сохраняется в файл.

### 5.6 Клиент: несколько узлов и выбор при старте

В `client.toml`:

```toml
remote_address = "203.0.113.10:443"
node_secret = "…"
node_public_key = "…"

[[nodes]]                       # запасные; у каждого свои учётные данные
address = "203.0.113.20:443"
node_secret = "…"
node_public_key = "…"
sni = "www.debian.org"
```

При старте клиент одновременно проверяет TCP-достижимость всех узлов и подключается к первому
живому (прошлый рабочий узел из `cache_dir/last_node` — первым). Смена узла посреди сессии
**намеренно не делается**: маршруты и kill-switch привязаны к адресу узла. Если все ноги мертвы
дольше `TUNNEL_DEAD_AFTER`, движок выходит сам, процесс завершается с ошибкой, сервис-менеджер
перезапускает клиент — уже с выбором следующего живого узла.

### 5.7 Число ног

В том же релизе число параллельных TCP-ног стало настройкой клиента: 1–10, по умолчанию 4
(`--tunnel-legs`, `tunnel_legs`, `SessionParams.tunnel_legs`, настройка в приложении). Предел 10 —
протокольный. Узлы старше релиза принимают не больше 4 ног.

## 6. Что дальше (проект)

| Этап | Что | Что перестаёт зависеть от центра |
|---|---|---|
| B | токены-способности с ослаблением (срок, подмножество узлов, роль), квоты приглашений; Ed25519 уже есть | допуск клиентов |
| C | зашифрованные дескрипторы в таблице с блайндингом по эпохам; точки встречи; парные секреты из статического DH вместо ключа роя | перечисление узлов, ключ роя |
| D | членство по поручительству ≥K, отзыв по цепочке приглашений | авторитеты |
| E | кредиты за ретрансляцию, слепые токены | биллинг |

Рубеж (bootstrap) клиента: подписанный набор достаётся любым из независимых каналов (кадр
`PeerHint` внутри живого соединения; CDN и облачные хранилища; DNS TXT/DoH с именами от даты и
ключа сети; почта и бот; соседи по локальной сети; волонтёры в браузере через WebRTC). Качается
набор целиком — хост канала не узнаёт, какие узлы нужны именно этому клиенту.

## 7. Модель угроз

| Противник | Что останавливает (этап A) | Что остаётся |
|---|---|---|
| Подделка записи | подпись, привязка `node_id` к ключам | — |
| Повтор старой записи / откат адреса | `seq`, срок жизни | — |
| Засорение каталога с одной сети | лимит на сеть, размер каталога, частота входящих | Sybil с разных сетей |
| Перечисление мостов через gossip | мосты не пересказываются | выдача мостов порциями (этап B/C) |
| Посторонний (без ключа роя) | не проходит тег `ClientHello` | утечка ключа роя |
| Захват узла | узел видит записи, но не секреты (они выводятся) | ключ роя у участника |
| Сборщик адресов (вступил как узел) | лимит на сеть; каталог не публикуется вне роя | цена = число узлов, не ноль |
| Блокировка адреса | запасные узлы в конфиге клиента | динамический рубеж (этап C) |
| Глобальный наблюдатель | — | не решается |

## 8. Ограничения прототипа

* Дайджест — окно из ≤ 480 пар; для тысяч узлов нужен компактный дайджест (IBLT/Merkle).
* Допуск mesh-пира — «знаю ключ роя», а не «владею этим узлом» (см. 5.4).
* Записи с публичными адресами; для имён хостов публичность проверить нельзя.
* Клиент не получает узлы из gossip автоматически: список в `client.toml` задаётся вручную
  (`PeerHint` — этап C).
* Время: записи опираются на часы; допуск расхождения 5 минут.
* Тесты: каталог — формат, правила допуска, сеть из 40 узлов, атаки (`cargo test -p netrunner-core --lib -- directory`); четыре
  теста с настоящими узлами по сокетам (обмен, чужой ключ роя, мосты, обычный клиент); выбор узла клиентом
  (`cargo test -p netrunner-client --features cli`).
