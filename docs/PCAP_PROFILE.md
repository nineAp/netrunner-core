# Браузерные профили: запись, JSON, загрузка

🇬🇧 [English version](en/PCAP_PROFILE.md)

Движок строит свой `ClientHello` по **профилю браузера** — «рецепту» отпечатка (шифры, группы,
подписи, порядок расширений…). Профиль — это данные: JSON-файл. Его можно **снять с настоящего
браузера одной командой**, отредактировать руками или написать с нуля, а клиент подхватывает его
при запуске. Никакой пересборки.

Один прогон записи даёт **три вещи** из одного файла:

| Что | Куда применяется |
|---|---|
| TLS-профиль (`ClientHello` по TCP) | TCP-ноги клиента |
| `quic` — QUIC Initial (`ClientHello`, транспортные параметры, раскладка пакетов) | UDP-нога клиента |
| `shape` — длины TLS-записей браузера | выравнивание длин записей клиента и узла |

Отдельно, для узла, снимается `cover-flight` — длины записей ответа вашего домена.

```text
 браузер ──трафик──▶ netrunner-client profile record ──▶ profile.json ──▶ netrunner-client --browser-profile profile.json
                      (AF_PACKET, без tcpdump)     (разбор pcap, JA3/JA4,        (движок строит ClientHello по JSON)
                                                    сборка, самопроверка)
```

## Быстрый старт

```bash
# 0. один раз: право на сырой сокет (или запускайте через sudo)
sudo setcap cap_net_raw+ep ./netrunner-client

# 1. ОТКЛЮЧИТЕ VPN, запустите запись и посёрфите в браузере 3–5 разных сайтов
#    (QUIC не отключайте: Chrome сам пойдёт и по TCP, и по UDP/443)
./netrunner-client profile record --out chrome.json
#    остановится само: набрано 12 соединений одного отпечатка (и, если пошёл QUIC, 4 его соединения),
#    либо по таймеру (120 с) или Ctrl+C

# 2. проверить (необязательно: record уже проверяет)
./netrunner-client profile check chrome.json

# 3. запустить клиент с этим профилем
./netrunner-client --config client.toml --browser-profile chrome.json
```

`browser_profile = "chrome.json"` можно положить и в `client.toml`, либо переменная
`NETRUNNER_BROWSER_PROFILE`. Файл с одним профилем или с **массивом** профилей — тогда каждая сессия
берёт один из них по хешу своего `session_id` (отпечаток стабилен всю сессию). Без флага
используется встроенный профиль.

Готовые профили: [`profiles/chrome_148.json`](../profiles/chrome_148.json) (снят с настоящего Chrome 148)
и [`profiles/minimal_example.json`](../profiles/minimal_example.json) (написан руками — шаблон для своих).

### Команды

| Команда | Что делает |
|---|---|
| `profile record --out F` | записывает трафик, строит профиль, проверяет движком, пишет JSON. Ключи: `--iface` (по умолчанию все), `--port` (443; можно повторять), `--seconds` (120), `--stop-after` (0 — только Ctrl+C/таймер; N — остановиться после N соединений одного отпечатка), `--save-pcap F`, `--name`, `--sni`, `--client`, `--ja4`, `--all`, `--min-hellos`, `--quic-ja4`, `--no-quic`, `--flight-sni`, `--flight-out` |
| `profile build CAP… --out F` | то же из готовых `.pcap`/`.pcapng` (Wireshark, `tcpdump`, Windows/macOS). Несколько файлов разбираются как один — например, прогон с QUIC и прогон с `--disable-quic` |
| `profile merge A B… --out F` | объединяет файлы профилей в один пул (дубли по JA4 отбрасываются, имена делаются уникальными) |
| `profile check F` | проверяет JSON (применим ли профиль к нашему протоколу, включая блоки `quic` и `shape`) и печатает предупреждения |

Ключи отбора: `--sni` (подстрока), `--client` (IP), `--ja4`/`--quic-ja4` (конкретная группа
отпечатков). `--all` снимает **каждый** отпечаток из захвата (Chrome + Firefox…) и пишет массив;
`--min-hellos` (по умолчанию 2) отсекает одиночных случайных клиентов вроде `curl`.

Запись показывает прогресс (TCP-соединений, `ClientHello`, QUIC, отпечатков), а в конце — сводку:
JA4, перемешивание расширений, наблюдавшиеся длины ECH, раскладку QUIC Initial, результат
самопроверки и замечания о том, что движок не воспроизводит.

> Чтобы определить **перемешивание расширений** и разброс длины ECH нужно несколько соединений:
> Chromium меняет порядок на каждом. Запись без VPN: иначе в захвате окажется наш же туннель.
> Чтобы получить QUIC-блок, нужны сайты с HTTP/3 (google.com, youtube.com, cloudflare.com).

### Самопроверка

Профиль, прошедший `validate`, лишь **применим** к протоколу. Поэтому после сборки `record`/`build`
делают то, что делает движок: собирают по профилю 24 `ClientHello` (и QUIC Initial'а), разбирают их
тем же парсером, что и захват, и сравнивают с браузером: JA4, набор расширений, наличие
перемешивания, длины ECH, размеры датаграмм, порядок транспортных параметров. Расхождение печатается
как `✘`, а команда завершается ошибкой (файл при этом записан — его можно осмотреть).

### Приватность

В JSON-профиль **не попадают** имена сайтов и IP-адреса из захвата (раньше в `meta` лежал SNI —
убрано, закреплено тестом). Но сырой захват (`--save-pcap`) содержит IP и SNI всего, что открывал
браузер: не публикуйте его и не пересылайте.

## Что записывается для узла

### Cover-flight: ответ вашего домена

Узел отвечает на «чужие» `ClientHello` записями, длины которых должны совпадать с настоящим ответом
сайта узла (`EncryptedExtensions`, `Certificate`, `CertificateVerify`, `Finished`). Снимите их **с
собственного домена**:

```bash
# на машине с браузером: откройте https://your.domain/ несколько раз в новых вкладках
./netrunner-client profile record --out chrome.json --flight-sni your.domain --flight-out flight.json
# на узле:
netrunner-server … --cover-flight /etc/netrunner/flight.json     # либо списком: --cover-flight 27,4342,537,69
```

Берутся полные рукопожатия TLS 1.3 (возобновлённые и TLS 1.2 не показывают `Certificate`); из них —
самый частый набор длин, а если наборы разные (балансировщик), выводится предупреждение. Без флага
используется типовая цепочка Let's Encrypt. Переменная: `NETRUNNER_COVER_FLIGHT`.

> Запись короче 41 байта поднимается до 41: меньше заголовка кадра cover-записи не бывает. У
> настоящих серверов `EncryptedExtensions` часто 23–30 байт, так что первая запись остаётся чуть
> длиннее настоящей — об этом предупреждает команда.

### Форма трафика

Длина TLS-записи видна наблюдателю. Блок `shape` хранит распределение длин записей браузера (до 256
квантилей на направление). Клиент использует `up`, узел — `down`: границы квантования набивки
подбираются из наблюдавшихся длин (по-прежнему не более 640 Б набивки на запись — КПД канала не
меняется). Узлу достаточно того же JSON:

```bash
netrunner-server … --shape-profile /etc/netrunner/chrome.json     # NETRUNNER_SHAPE_PROFILE
```

Нужно ≥ 8 значений на направление; меньше — форма для него не применяется (запись предупредит).
Учитываются только длины записей по направлениям; временна́я картина и конкретный сайт не
воспроизводятся.

## Формат JSON (schema 1)

Числа — числом или строкой `"0x1301"`; расширения — числом, `"0x…"` или **именем**. Неизвестные
поля отвергаются (опечатка не пройдёт молча).

| Поле | Обяз. | Смысл |
|---|:-:|---|
| `schema` | — | версия формата, сейчас `1` |
| `name` | да | имя (1–64 символа) |
| `record_layer_version` | да | версия в заголовке TLS-записи с `ClientHello`: `0x0301` (Chrome), `0x0303`, `0x0304` |
| `cipher_suites` | да | шифры **без GREASE**; `0x1301` или `0x1302` обязателен (узел по умолчанию выбирает AES-GCM) |
| `groups` | да | `supported_groups` без GREASE; **обязателен `0x001d`** (x25519), `0x11ec` добавляет постквантовый балласт |
| `signatures` | да | `signature_algorithms` |
| `delegated_signatures` | — | для `delegated_credential` |
| `versions` | да | `supported_versions` без GREASE; **обязателен `0x0304`** |
| `alpn`, `alps_protocols` | — | протоколы ALPN / ALPS |
| `alps_codepoint` | — | `0x44cd` (по умолчанию) либо `0x4469` |
| `extension_order` | да | порядок расширений; `grease_first` / `grease_last` — позиции GREASE. Обязательны `key_share`, `supported_groups`, `supported_versions` |
| `has_grease` | — | по умолчанию — есть ли GREASE-слоты в порядке |
| `shuffle_extensions` | — | перемешивать «середину» порядка на каждое соединение (Chromium) |
| `target_padding_len` | — | цель паддинга `ClientHello` (0 — без) |
| `ech_payload_lengths` | — | допустимые длины payload GREASE-ECH; на соединение берётся случайная (пусто = 144) |
| `compress_cert_algs`, `psk_modes`, `ec_point_formats` | — | содержимое одноимённых расширений (по умолчанию brotli, `[1]`, `[0]`) |
| `raw_extensions` | — | тела расширений без собственной сборки: `{"0x1234": "abcd01"}` — выписываются как есть |
| `quic` | — | блок QUIC (ниже) |
| `shape` | — | `{"up": [...], "down": [...]}` — длины TLS-записей, по возрастанию |
| `meta` | — | любые сведения (источник, JA3/JA4, заметки); движком не читается |

Имена расширений: `server_name`, `status_request`, `supported_groups`, `ec_point_formats`,
`signature_algorithms`, `alpn`, `sct`, `padding`, `extended_master_secret`, `compress_certificate`,
`delegated_credential`, `session_ticket`, `supported_versions`, `psk_key_exchange_modes`, `key_share`,
`alps`, `ech`, `renegotiation_info`, `grease_first`, `grease_last`.

### Блок `quic`

| Поле | Смысл |
|---|---|
| `hello` | `ClientHello` QUIC — тот же формат, что и весь профиль (вложенный `quic` запрещён). В `extension_order` стоит `"0x0039"` (`quic_transport_parameters`); тело движок подставляет сам |
| `scid_len` | длина Source Connection ID клиента (Chrome — 0) |
| `pn_len`, `first_pn` | длина кодируемого номера пакета и номер первого пакета (Chrome — 1) |
| `initial_packets` | раскладка первого полёта: `[{"crypto": 890, "datagram": 1250, "pn_len": 2}, …]` — сколько байт `ClientHello` несёт пакет и какого размера датаграмма (добивается PADDING до ≥ 1200, RFC 9000 §14.1) |
| `scramble_frames` | Chrome «взбивает» Initial: `ClientHello` режется на много CRYPTO-кадров, они идут вперемешку с PING и PADDING и разложены по пакетам непоследовательно. Включено — движок делает то же |
| `shuffle_transport_params` | порядок транспортных параметров случаен на каждое соединение |
| `transport_params` | `[{"id": "0x0001", "value": "80007530", "kind": "fixed"}, …]`; `kind`: `fixed` — как есть, `scid` — подставляется SCID пакета, `grease` — зарезервированный параметр (`31·N+27`: идентификатор того же класса длины и случайное значение той же длины на каждое соединение), `version_information` — GREASE-версии в списке заменяются свежими |

Остаётся зашитым — **длина DCID (8 байт) и версия QUIC (1)**: по DCID узел находит сессию, это
параметр протокола между нашими клиентом и узлом, а не отпечаток. Содержимое Initial узел не
разбирает.

Профиль **проверяется при загрузке**: если он ломает протокол (нет x25519, TLS 1.3, `key_share`,
AES-GCM-шифра, дубль расширения, датаграмма Initial короче 1200 Б, номер пакета не помещается в
`pn_len`…), загрузка отклоняется со списком причин и ничего не меняется — ошибка видна сразу, а не на
первом соединении. Менее серьёзное (расширение без сборщика и без `raw_extensions` будет пропущено…)
выводится предупреждением.

## Что извлекается из захвата

**TLS по TCP.** Из каждого `ClientHello`, без потерь: версия в заголовке записи, `legacy_version`,
шифры (с GREASE), расширения **в порядке на проводе**, SNI, группы, подписи, ALPN, ALPS (кодпоинт),
`key_share` (группа и длина каждой доли), PSK-режимы, форматы точек, `compress_certificate`,
`status_request`, ECH (`enc`/`payload`), паддинг, фрагментация по записям. Из ответа сервера —
`ServerHello` и длины записей первого flight'а; из остальной части соединения — длины записей
`ApplicationData` в обе стороны.

**QUIC.** Initial-пакеты шифруются ключами из публичной соли и открытого DCID (RFC 9001 §5.2), так
что `ClientHello` достаётся без чьих-либо секретов — как у любого DPI. Парсер снимает защиту
заголовка, расшифровывает AES-128-GCM, разбирает кадры (CRYPTO/PING/PADDING/ACK), склеивает
CRYPTO-поток по смещениям из нескольких пакетов и датаграмм, разбирает транспортные параметры.
Поддерживается QUIC версии 1; другие версии пропускаются с замечанием. Повторные отправки Initial
по таймеру в раскладку не входят, дубли пакетов (loopback отдаёт исходящий и входящий экземпляр)
отбрасываются.

Считаются **JA3** и **JA4** (для QUIC — с префиксом `q`); JA4 не зависит от GREASE и порядка, поэтому
профиль, пересобранный движком, обязан дать тот же JA4, что и браузер — это проверяется тестами и
самопроверкой.

Если в захвате несколько разных клиентов, берётся самая многочисленная группа по JA4 (остальные
перечисляются); `--sni`, `--client`, `--ja4`, `--all` выбирают нужное. QUIC-группы привязываются к
TCP-профилям по порядку частоты (движок выбирает QUIC-блок независимо от TCP-профиля сессии).

## Ограничения: откуда они и что с ними

| Ограничение | Откуда | Состояние |
|---|---|---|
| Профиль был константой в коде | архитектура | **снято**: JSON, загрузка при старте, `--browser-profile` |
| ECH-payload — константа 144 Б (у Chrome случайный 144/176/208/240) | зашито в сборщике | **снято**: `ech_payload_lengths`, случайная на соединение |
| Зашитые brotli / PSK `[1]` / формат точек `[0]` / ALPS `0x44cd` | зашито в сборщике | **снято**: поля профиля |
| Расширения без сборщика **молча пропускались** | сборщик | **снято**: `raw_extensions` (тело из захвата); без тела — предупреждение |
| Нужно `tcpdump` и права | инструмент | **снято**: запись из бинаря (`AF_PACKET`, `CAP_NET_RAW`) |
| В профиль попадал SNI посещённых сайтов | `meta` | **снято**: имён сайтов в JSON нет |
| Профиль не проверялся на воспроизводимость | — | **снято**: самопроверка движком при записи |
| Один отпечаток на захват | — | **снято**: `--all`, `profile merge` |
| QUIC не разбирался | парсер | **снято**: Initial расшифровывается, блок `quic`, движок собирает Initial по профилю |
| Длины записей — синтетика | — | **снято**: блок `shape`, `--shape-profile` у узла |
| Cover-flight — типовая цепочка | — | **снято**: `--flight-out` / `--cover-flight` |
| Запись только на Linux | `AF_PACKET` | на macOS/Windows: `profile build` по `.pcap` из Wireshark. Нативный захват (libpcap/Npcap) — возможное расширение |
| Не воспроизводится: `legacy_version`≠`0x0303`, `session_id`≠32 Б (TCP), `compression`≠`[0]`, нестандартные `key_share`/`status_request`/SCT/EMS/ticket | **протокол**: в `session_id` едут версия, шифр и тег; обмен ключами — только X25519 | остаётся; такие отличия выводятся в `notes` |
| Длина DCID (8 Б) и версия (1) QUIC | **протокол**: по DCID узел находит сессию | остаётся |
| Запись < 41 Б в cover-flight | заголовок кадра cover-записи (25 Б) + тег (16 Б) | остаётся; команда предупреждает |
| Не воспроизводятся: TCP/IP-отпечаток ОС (MSS, окно, TTL), 0-RTT и возобновление сеанса, HelloRetryRequest, QUIC Retry/токены, повторные Initial по таймеру | ядро ОС / отдельные сценарии | остаётся |
| Форма — только длины записей | временна́я картина и конкретный сайт не снимаются | остаётся |
| Мобильное приложение (UniFFI) не принимает JSON-профиль | нет параметра в `SessionParams` | **можно доработать**: добавить параметр; `core::browser_profile::load_json` уже готов |
| UDP-нога WebRTC | нет профиля из JSON | возможное расширение |
| Нужно начало соединения | TCP/TLS: `ClientHello` — первый пакет | неустранимо, но запись ловит новые соединения; открывайте новые вкладки |
| Firefox headless не снялся при проверке | окружение (Firefox-snap), не инструмент | снимите профиль на своей машине; парсер Firefox-образной ветки проверен на синтетике |

## API

```rust
use netrunner_core::{browser_profile, pcap};

// движок: подмена встроенного пула своими профилями (TLS, QUIC, форма трафика)
let report = browser_profile::load_file("chrome.json")?;      // или load_json(&str)
browser_profile::clear();                                      // вернуть встроенные
browser_profile::load_shape_file("chrome.json")?;              // только форма (узел)

// снятие: файл(ы) → профиль
let analysis = pcap::analyze(&std::fs::read("chrome.pcap")?)?; // или analyze_many(&[..])
let profile = analysis.build_profile(&pcap::ProfileOptions::default())?;
let quic = analysis.build_quic(&pcap::ProfileOptions::default())?;
let ok = analysis.verify_profile(&profile, pcap::DEFAULT_SAMPLES).unwrap().ok();
let flight = analysis.measured_flight("your.domain")?;        // для --cover-flight
std::fs::write("chrome.json", profile.to_json())?;

// запись (Linux), feature `pcap`
let rec = pcap::capture::record(&pcap::capture::CaptureConfig::default(), &stop, &mut |p| { /* прогресс */ })?;
let analysis = rec.analyze();
```

Низкоуровневые части (`read_packets`, `assemble_flows`, `split_records`, `parse_client_hello`,
`quic::parse_initial`, `ja3_string`, `ja4`) публичны. Модуль `pcap` включается feature `pcap`; чтение
JSON (`browser_profile`) доступно всегда, в том числе в мобильных и wasm-сборках.

## Проверка

```bash
cargo test -p netrunner-core --features pcap --lib      # 302 теста
```

Один из них (`garbage_client_hello_triggers_fallback_without_hanging`) ждёт ответа DNS и в окружении
без сети падает по таймауту — к профилям он не относится (падает и без этих изменений).

Среди тестов: синтетические захваты из `ClientHello` нашего же сборщика; **реальный захват Chrome 148**
по TCP и по QUIC (фикстуры `core/src/pcap/testdata/chrome148_loopback.pcap`, `chrome148_quic.pcap`) →
JSON → профиль → пересборка с тем же JA4; ключи Initial — по векторам RFC 9001, Приложение A; сотни

### Что нашлось на реальном Chrome 148

| Наблюдение | Значение |
|---|---|
| JA4 (TCP) | `t13d1516h2_8daaf6152771_d8a2da3f94cd` (`8daaf6152771` — известный хеш шифров Chrome) |
| `signature_algorithms` | 8 значений, **без ML-DSA** (`0904`–`0906`); в встроенном `CHROME_140` их 11 |
| порядок расширений (TCP) | перемешивается между соединениями; набор из 18 (с 2 GREASE) совпадает с `CHROME_140` |
| ECH GREASE payload | случайный: 144 / 176 / 208 / 240 B |
| первый flight (RSA-2048 `s_server`) | записи `23, 832, 281, 53` (`Finished = 4+32+17 = 53`) |
| JA4 (QUIC) | `q13d0311h3_55b375c5d22e_653d80c3fe9d`: 3 шифра, 11 расширений, **без GREASE-расширений**, ALPN `h3`, ALPS, ECH |
| Initial | два пакета по 1250 Б (один ClientHello ≈ 1780 Б не помещается), номера с **1**, длина номера 1–2 Б, SCID пустой, DCID 8 Б |
| кадры Initial | **«взбиты»**: до двух десятков CRYPTO-кадров на пакет разной длины (1–800 Б), PING, PADDING кусками, смещения непоследовательны; при повторной отправке раскладка заново случайна |
| транспортные параметры | 12 штук в **случайном порядке**; GREASE-параметр с 8-байтным идентификатором и 8–15 Б значения; `version_information` с GREASE-версией в случайной позиции |
| повторные отправки | по таймеру (≈ 0,3 / 0,9 / 2,1 / 4 с) |

Встроенный `CHROME_140` отличается от Chrome 148 списком подписей, и встроенный Initial UDP-ноги
выглядит иначе (один Initial, один CRYPTO-кадр, 7 расширений без ECH и ALPS, 3 шифра, 8 транспортных параметров) — используйте
`profiles/chrome_148.json` (или снимите профиль под свою версию браузера).
